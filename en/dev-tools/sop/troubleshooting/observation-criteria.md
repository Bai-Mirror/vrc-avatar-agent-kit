# Troubleshooting · Observation criteria

> **Before reporting "X didn't take effect", ask three things:**
> Was this observation taken at the **right moment**? Is the **criterion** right? Does **the check script itself** have a bug?
>
> **Confidently reporting a wrong conclusion costs far more than saying "I'm not sure".**

## Wrong moment

| Scenario | Wrong criterion | Right criterion |
|---|---|---|
| Just entered Play | The animator hasn't evaluated yet; NDMF hasn't finished generating | Run a few frames first; or switch parameters manually with Gesture Manager |
| Parameter audit | At edit time you can't see the parts generated at build time by MA/VRCFury/MenuInstaller | **Run it in Play mode** (measured: at edit time 24 parameters, 108 bits → after build 92 parameters, 177 bits) |
| Material verification | Guessing by reading prefab YAML | Write a probe script and have Unity report the runtime true values |

## Wrong criterion

**① Platform override vs. default tier.**
Editor rendering **always uses the default tier**. If you changed an Android/WebGL platform override, editor screenshots **cannot possibly** reveal the problem.
> Hit before: pushed a group of textures' WebGL override down to 64 (default tier still 2048); everything looked normal in the editor,
> but on a real device 167 prefabs turned entirely white.

**Corollary**: performance changes (texture budgets, compression formats, mesh compression, shader stripping) all belong to this category.
Either verify on a real device, or **explicitly mark "this item not verified on a real device"** in the report.

**② lilToon's feature toggles are `_UseXxx`, not `_XxxBlend`.**
With `_MatCapBlend: 1` but `_UseMatCap: 0`, that layer doesn't take effect at all;
a missing texture reference in that slot is **inert, not a bug**.

**③ Linear color space.**
If the project is `m_ActiveColorSpace: 1`, `.mat` files store linear floats while the Inspector shows sRGB.
**Describing colors from the numbers in the file will be wildly wrong.**

**④ Skinned bounds are chronically inflated.**
`SkinnedMeshRenderer.bounds` was measured reporting a 0.755 m base avatar as 2.24 m, and a 1.15 m one as 2.38 m.
Measure height using **Head/Foot bone world coordinates**; for precise framing, **render a chroma-key probe and measure back**
(the two-pass framing in `通用工具/AvatarPortrait.cs`).

**⑤ The parent of a stripped Transform must be traced back.**
For objects attached to base avatar bones, the parent fileID points to a stripped Transform;
you must follow `m_CorrespondingSourceObject` back to the source prefab to know the real attachment point.
Collapsing every stripped parent to the prefab root will misjudge "two objects attached to the left and right index fingers respectively"
as "duplicate instances with the same parent and coordinates".
Also, base avatar bones come from FBX import; their fileIDs are hash-generated by Unity and appear in no text, so **bone names cannot be reverse-resolved**.

**⑥ Don't judge outfit compatibility by file name.** → [50 Fitting](../50-outfit-and-hair-assembly.md)

## The check script itself has a bug

> Measured: wrote a cross-block non-greedy regex to re-check animation curves, and reported "the file wasn't cleaned up" based on it.
> **It had actually been correct long before** — the regex crossed into the adjacent curve block and picked up unrelated values.

**Practice**: run the check script once on a **known-correct** sample and once on a **known-wrong** sample, confirm it can tell them apart, and only then use it to draw conclusions.

## Single-model visual judgment is untrustworthy

Models will report defects that **don't exist at all** with confidence 1.0, and **self-reported confidence does not predict truth at all**.
> Measured (2026-09-01 showcase shot review): all 4 items flagged by ≥2 models were true;
> of the 17 items flagged by a single model, "Project F feet cropped" and "Project F overexposed" were, on re-check, **both hallucinations**.

**Rule**: use the three-tier setup from [05 · Multi-model review procedure](../05-multi-model-review.md) (`通用工具/agy_panel.py`): for daily `--fast` single-model quick reviews, treat every finding as "to verify" and re-check it yourself;
at major milestones cross-check with 3 models; **only findings independently flagged by ≥2 models are accepted directly**; single-model findings are downgraded to "to verify" — **neither discarded nor trusted outright**.

## "Done" doesn't mean "looks right"

A log saying "completed N segments" only proves the code ran to the end, not that the thing looks right.
**Only images can prove the correctness of visual assets**, and from **at least three angles**.
> Hit before: the fence-replacement campaign produced, in a row: shrunk to 1% / whole row rotated 90° / everything floating 1.64 m / gate opening 50% too large / one section missing at the east end;
> **all five problems were found by the user looking at images** — each time I fixed one, I shot only one angle and declared it done.

## The source scene is not the delivered state

<a id="源场景不等于交付态"></a>

**Numbers measured on the source scene cannot be used to determine the behavior of the delivered build.**
The build pipeline (NDMF / Modular Avatar / mesh optimizers) substantially rewrites the project at bake time:

| Source scene | After bake | Who changed it |
|---|---|---|
| One SkinnedMeshRenderer per part | Merged into a few | Mesh optimizer's automatic merging |
| Each renderer's own `localBounds` | Rewritten uniformly | `MA MeshSettings` (rootBone + bounds + probe anchor) |
| Controller layer indices | Renumbered after merging | Each MergeAnimator appends in order |
| Playable layer masks | Taken from "the avatarMask of merged layer 0" | NDMF / VRCFury always override the field on the descriptor |
| PhysBone component count | Noticeably more (armature merging for outfits copies one each) | Armature merging |

**Instance hit before**: in the source scene, each renderer of a certain hairstyle had bounds of only 0.1–0.5 m, looking like a classic
"bounds too small causing frustum culling"; after changing it accordingly, the symptom became **permanent** instead.
Only measuring after baking revealed: the renderers had been merged into one, `MA MeshSettings` had uniformly set the bounds to 2×2×2,
with 0 out-of-bounds bones — **small bounds did not exist in the delivered build at all**; I was treating a disease that didn't exist.

**Rules**:
- For any property that "may be rewritten at build time" (bounds, masks, layer indices, renderer count, component count),
  **the criterion must be taken on the baked clone**.
- Write diagnostic scripts to "measure the clone first if one is in the scene", and **print out** which one was measured.
- Baking is expensive; don't loop-tune with it; after measuring, clean up the clone — don't leave it in the scene.

## Rendering and framing: the image was rendered ≠ anything was drawn

**Log all PASS, image a solid color**; render batchmode must not add `-nographics`;
shooting several sets in a row requires reloading the scene per set or you get duplicate images; a tool's master copy and project copy diverge;
measuring pixel differences by zone first requires proving you're measuring that body part; **after changing blend shapes at edit time, render twice** — a single render captures the old skinning.
All six come with triggers and criteria → **[Observation criteria / Rendering and framing](observation-criteria/rendering-and-framing.md)**

> Remember in one sentence: **"wrote xxx.png 1500x1500" only proves the file was written, not that anything was drawn on it.**
> Before sending for review, run `getextrema()` first; after shooting in a row, do pairwise pixel diffs first.

> → [The criterion itself may be broken (four failure modes and self-checks)](observation-criteria/criterion-may-be-broken.md) — the observation channel can't render the target phenomenon; for "can't see it", check the Scene/Game view first; probes report missing values as legal ones; if resolution isn't enough, push parameters to extremes; the criterion's direction may be backwards (first ask "would deleting the object under test make the metric better?").
