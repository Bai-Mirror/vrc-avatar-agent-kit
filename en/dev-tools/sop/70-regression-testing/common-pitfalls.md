# 70 · Common pitfalls (hit in real runs)

> ← [70 · Regression test](../70-regression-testing.md). Trigger: when a tool behaves abnormally halfway through an audit, or a whole T1 read-back batch is aborted.

- **`execute_code`/menu timeouts and resends, lock timing, how to write heavy jobs >20 s per call, native crashes during builds** → [Editor invocation and resend](common-pitfalls/editor-invocation-and-resend.md) (tested multiple times 09-21/22).

- **Entering Play is not a build entry point**: T1/T4 only run in a self-opened session on already-built output with all Play preprocessing entry points isolated; for the exact prerequisites and the items not yet in place, see [Play entry points and blockers](common-pitfalls/editor-invocation-and-resend.md). The old record "enter Play and wait for the NDMF build" only describes the old flow and must not be followed; high CPU / being able to make lightweight calls proves nothing about whether a build was re-triggered. If new preprocessing logs appear, stop this measurement, record it as not tested, and recover per the environment page; don't rely on repeatedly entering Play and hoping for luck.
- Before quitting Unity, read `scene.isDirty`, otherwise it may hang on the save dialog ([This machine (Linux) environment](../02-environment-and-manual-intervention/b850-linux-environment.md)).
- T1 v4 read-back assertion: a parameter that is clamped / legitimately rewritten by a driver aborts the whole batch; read `audit.log` to see which parameter.
- Parameter values in the output JSON are echoed with 6 decimal places (`AuditIO.cs` `0.######`); to infer the request from the output, recompute the exact fraction; check tier by tier "is value < i/n?" rather than a blanket "everything is shifted". Before writing samples, check the project's menu document for what each tier means; don't infer backwards from scanned values.
- **When you take over a project and the first Play looks wrong, check these three in order** (tested on the old version before 09-18, still valid): ① FX-layer parameter defaults override the settings in the scene — **the defaults must be changed in both** `ExParameters.asset` and the controller; ② a resident high-priority MergeAnimator layer (`layerPriority: 999` + unconditionally resident) flattens every expression that uses the same-name keys; ③ expressions extrapolating beyond 0–100 (check modified expressions, and re-check those judged "safe" too, [Bake and compensation](../30-face-sculpt/baking-and-compensation.md)).
- Identify the body by skinning weights, not by name ([Shape of a criterion](../troubleshooting/observation-criteria/shape-of-a-criterion.md)).
- **Play read-back passing ≠ working after upload** (2026-09-20, Project A): GestureManager drives any parameter in FX directly, so even a parameter missing from the post-build expression parameter table still "reads back correctly". The generator wrote MA Parameters only to `_Menu` under the original root; the copy on the face-tracking clone root stayed on the old table, and `A2_HairColor`/`A2_HoleHeel`/all 6 pet parameters were missing — the 09-19 hair-color radial passed Play acceptance entirely yet was broken. Whenever new parameters are added: in Play, read the descriptor's `expressionParameters` (the post-build Clone) to confirm the names are in the table, or run T4 and check `menu_params_undeclared`=0. In multi-root projects the **values** written by the generator (not just references) must also be synced to the clone root.
- **Default reset washes away "toggle residue"** (2026-09-20, Project B): state requests default to `"reset":"declared"`, which resets user-controllable parameters to their declared defaults before applying each state — this isolates states, but also erases residue from the previous step, **and the residue is exactly what needs testing**. Measured: under the default mode, "shoes off" at the 43% tier read back all foot keys as 0 and looked fine; the user, **clicking the menu in sequence** in GestureManager, saw the keys still on. When the user reports "after turning off X, Y is still there" or "it's wrong after switching back", use `"reset":"none"`, write a **click sequence** as multiple states inside one state step (the first state lists all parameters, each subsequent state lists only the one that changes), walk through it the way it is really clicked, and read back at each step. Run both modes: `declared` judges "is this state itself correct", `none` judges "is it correct when switched to from another state".
- **For poke `patch_count: 0`, first check whether `pairs` is empty** (2026-09-20, Project B): pairing only recognizes **request-level** `poke_covers` (or `poke_decl` pointing to decl.json); writing it into `poke.covers` is **silently ignored** → `pairs: []` → `patch_count: 0`, `total_patch_area_cm2: 0`. That 0 means **not tested**, not "no poke-through", and it looks exactly like a pass. Queryable question: **"How many pairs are behind this 0?"** If the pair count is 0, treat it as `undecidable` and keep it out of conclusions. (R9 `candidates` uses the candidate's own `garment`+`covers` and is unaffected by this; `pair_confidence=high` is trustworthy.)
- **Give `covers` according to what this garment** actually **covers** (2026-09-20, Project B): I put `LeftLowerLeg/RightLowerLeg` into the covers of low-top sneakers, so "calf showing outside the shoe" was treated as poke-through — the `leftlowerleg` segment p50 = +119 mm, outside = 305 vertices, and it even produced a 0.85 cm² patch. Shoes can't cover the calf; all those numbers were my own fabrication. Queryable question: **"For every bone in covers, can this garment really cover it?"** Conversely, giving too few covers misses tests (this time the ankle wasn't included at first).
- **When copying an old request as a template, you must rewrite `out` step by step** (2026-09-20, Project B): each step of `sequence` carries its own `out`, and the top-level `out` does not override it. I copied `seq_play_0920.json` into a new request and changed only the top-level `out`; after the run I found the 6 steps had **overwritten the morning's R9 output in place** (the new directory held only `audit.log`/`sequence_status.json`; the real output was written back into the old directory). It was only restored via `git checkout --`. Queryable question: **"Does every step's `out` in this request point to the new directory I intend to write this time?"** Trade-off: better to generate the request fresh every time (assemble `out` in a script) than to hand-edit old JSON.
- **A build timeout is not a failure** (09-21, Project B old flow; entry point corrected 09-23): an old MCP build kept running after timing out and generated about 445 MB of assets. Current full builds / preprocessing are always batch-mode and serialized machine-wide; stages, errors and the final criterion must still be written to files. On timeout, check the log / completion file first; don't resend, and don't re-run it in the interactive editor. Running NDMF alone via `ProcessAvatar` is not the full SDK chain. Temporary clones are destroyed once measurement/persistence completes; `legacyClampBlendShapeWeights` and any settings changed this time are restored to the pre-session snapshot and read back; a clone that references a temporary generated directory cannot be treated directly as a finished product reusable across sessions.
- **The build output is the only trustworthy answer to "who overrides whom"** (2026-09-21, Project B):
  To tell whose layer comes later between two MA MergeAnimators, don't guess from `layerPriority`, and don't infer from the object hierarchy.
  Run one build, print the FX's `ctrl.layers[i].name` together with "which paths this layer's clips write",
  higher index is later, and the later writer wins. That is how Project B's socks confirmed that `Slot_Sok`(93) really sits after
  the vendor's `LEM/LooseSocks`(84), which is what made the plan valid.

- **Waiting in the background with `pgrep -f "<keyword>"` to detect that the other process ended will wait forever** (twice on 09-22): `-f` matches the whole command line, and the waiting script's own command line contains the keyword, so it always matches itself.
  **How to write it**: put a character class in the keyword, e.g. `pgrep -f "[d]sh_meteor33"` (the regex matches `dsh_meteor33`, but its own command line reads `[d]sh…` and does not match); or wait directly on the other process's PID (`while kill -0 <pid>`).
  > **Queryable question**: does the text of my wait command itself contain the string it is looking for?
- **Screenshot/measurement tools turn renderers off in memory; the restore check must include `Renderer.enabled`** (09-22, Project A): comparing only the hierarchy md5 (path/activeSelf/position) misses an unrestored `enabled=false`, and the next task that saves writes 735 entries of `m_Enabled=0` into the scene. **What to do**: before a read-only task wraps up, reload from disk with `EditorSceneManager.OpenScene(path)`; a task that modifies the scene also reloads as its very first step before touching anything.
