## 1. Deployment

Since T-09 everything goes through `开发工具/通用工具/审查/perception/sync_audit.py`. The landing location (decided by the user at 21:40, P4) is
`<工程>/Assets/AvatarAudit/{Runtime,Editor}`, each with its own asmdef; the old `<工程>/Assets/Editor/AvatarAudit/`
(no asmdef, compiled into `Assembly-CSharp-Editor`) is cleaned up automatically by the script.

```bash
# 1) Look at the plan first (no disk changes)
python3 开发工具/通用工具/审查/perception/sync_audit.py "<工程>" --dry-run
# 2) Real sync
python3 开发工具/通用工具/审查/perception/sync_audit.py "<工程>"
# 2b) When the source workspace is half-finished: take from a specified revision (task AR)
python3 开发工具/通用工具/审查/perception/sync_audit.py "<工程>" --from-git HEAD
# 3) Strip before delivery (T-23)
python3 开发工具/通用工具/审查/perception/sync_audit.py "<工程>" --strip --dry-run
python3 开发工具/通用工具/审查/perception/sync_audit.py "<工程>" --strip
# 4) Script self-test (temporary fake project + temporary git repo, doesn't touch real projects)
python3 开发工具/通用工具/审查/perception/sync_audit.py --selftest
```

`--from-git <rev>` (off by default): instead of rsyncing the workspace, fetches content file by file with `git show <rev>:<源路径>`;
the `VERSION` hash is also computed from the git content; stale files are still cleaned per `--delete` semantics; when the workspace has uncommitted changes (including untracked),
it prints a ⚠ warning and lists each item. Its purpose is “while DSH is modifying `审查/unity/`, don't copy the half-finished work into the project”.

Sync does three things:

1. `rsync -a --delete` lays `审查/unity/` (`Editor/` + `Runtime/`) out into `<工程>/Assets/AvatarAudit/`.
   `*.meta` and `VERSION` are excluded from both syncing **and deletion** — `.meta` is generated by Unity, and if rsync deleted them on a rerun
   all GUIDs would change; when a file is deleted from the source, the script separately cleans up its orphan `.meta`.
2. Deletes the old location `<工程>/Assets/Editor/AvatarAudit/` (together with its own `.meta`). **Only these two paths are deleted**:
   other files under `Assets/Editor/` aren't touched, and an emptied `Assets/Editor/` isn't deleted either.
3. Writes `<工程>/Assets/AvatarAudit/VERSION`:

   ```
   # AvatarAudit deployment marker —— 由 开发工具/通用工具/审查/perception/sync_audit.py 生成，勿手改。
   source: 开发工具/通用工具/审查/unity
   hash: <64 位 sha256>
   time: <UTC ISO8601>
   files: <N>
   ```

   `hash` is a deterministic digest of the `审查/unity/` file tree (sorted by relative posix path, feeding `<路径>\0<字节>\0` per file,
   independent of mtime/absolute paths); T-13's `tool_version` stamp is based on it.

Before deleting the target directory there's a fingerprint check: if the directory doesn't contain this deployment's asmdef / VERSION / audit source, it refuses unless `--force`.
`--strip` is the reverse operation (for T-23 stripping before delivery): deletes `<工程>/Assets/AvatarAudit/` and the old location, without writing VERSION.

- **Don't run sync against a project directly from your own side** (Unity may be open) — hand the command to Claude, and after deployment, in Unity,
  `refresh_unity` → `read_console` to confirm 0 errors.
- Unity generates `.meta` itself; no need to write them by hand.
- Put request files in `<工程>/Library/AvatarAudit/request.json`: `Library/` isn't in version control and isn't imported by Unity.
- The output directory is determined by `out` (absolute path) in the request; recommended:
  `<工作区>/_长程任务_20260918/审查产出/<工程>/<run>/`.

## 2. Invocation

| Menu item | Role |
|---|---|
| `Tools/AvatarAudit/Run Request` | Reads `<工程>/Library/AvatarAudit/request.json` → dispatches by `"tool"` → runs to completion |
| `Tools/AvatarAudit/Abort Current Run` | Aborts the current run, writes error to `status.json`, and goes through Cleanup |

- The whole process doesn't block the main thread: `EditorApplication.update` advances one step per frame (one T1 state stage / one T3 viewpoint).
- During the run it writes `<out>/status.json`:
  `{"state":"running|done|error|aborted","progress":"3/20","message":"...","tool":"state","time":"..."}`
  (`aborted` = the T-13 sentinel didn't pass / state read-back assertion mismatch; data is kept but the whole batch is invalidated; see §3.3)
- Errors are written to `message` in `status.json`, and a full stack trace is also kept in both `<out>/audit.log` and the Console.
- **T1 must be in Play mode**. When not in Play, by default it only writes one error (prompting to press Play first); only with `"auto_play": true` in the request
  does it automatically `EnterPlaymode()` and continue after entering (using `SessionState` to resume across domain reloads).
  Note: when the scene has unsaved changes Unity pops up a save dialog, and auto-entering Play will get stuck — in automated scenarios, it's recommended that the caller press Play first.
- **Chaining T1 → T3**: at the end, T1 **deliberately keeps the parameter values of the last state** (no reset), so within the same Play session,
  once T1 finishes, just send a `tool=turntable` request to capture that batch of states; T3 itself doesn't set any parameters.
- **Chaining multiple requests into one trigger**: `{"tool":"sequence", ...}` can run multiple T1/T3/T4/fit
  sub-requests in order within one menu trigger (batch “per outfit set state → render” doesn't require triggering the menu dozens of times); see §13.
