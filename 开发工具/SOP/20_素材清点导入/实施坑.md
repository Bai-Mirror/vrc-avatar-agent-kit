# 素材清点的实施坑

这页解决的问题：**清点/使用率这类统计跑出来的数看着都合理、一个都不报错，但可能全是错的。**
三个已经踩过的判据坑，加上出数之前必做的反查。

---

## 一、三个已经踩过的判据坑

| 坑 | 症状 | 正解 |
|---|---|---|
| 按**目录名**猜商品对应 | 全错。「揺れるハートのリング」解出来叫 `HINO shop`，「Makeup & Eye Texture」叫 `cumulus` | unitypackage 里带原始 GUID，跟工程 `.meta` 取交集 |
| 用**扩展名**判断条目是不是文件 | `.prefab`（6 字符）被当成目录漏掉，而预制体正是场景引用的主体 →「引用」列大面积假 0 | 目录 = 它是另一个条目的父路径。unitypackage 里目录和文件同列，这个判据是确定的 |
| 可达性从 `Assets/**/*.unity` 出发 | 厂商演示场景（插件自带的 Generator / Sample Scene 之类）把整包资产全标成「用上了」 | **只从自己的工作场景出发** |

---

## 二、统计类判据，出数之前先证伪

上面三个坑有个共同点：**跑出来的数看着都合理，没有一个报错。**

凡是「覆盖率 / 使用率 / 完整性」这类统计，出数之前必须先做一次**已知答案的反查**：

1. 挑一个**确定用了**的素材 → 它的数必须 **> 0**
   > 实测反例：某插件明明挂在头像上却显示 0。这个反查第一轮就该主动做，
   > 而不是等表都填完了才偶然发现。
2. 挑一个**确定没用**的素材 → 它的数必须 **== 0**
   > 实测反例：某配饰刚导入、没装到头像上，却显示 56。
3. 两头都对上，这张表才可以拿去做决定。

> 不限于素材统计。**断链扫描、参数预算、性能报告，凡是「数出来的结论」都适用。**
> 代价是两分钟，不做的代价是整轮返工。

---

## 三、工具化和查证要分开做

边查错边把一次性脚本升级成通用工具，会让时间翻倍。

**正确顺序**：先用最粗的方式把答案拿到手交出去，**工具化是下一件事**。
两件事缠在一起时，每次判据修正都要重跑全量，还会连带把补丁脚本改坏。

> 写补丁脚本别用 shell heredoc 传含 `\n` 或反引号的内容 ——
> 反引号会被当命令替换，`\n` 会变成真换行撑破 C#/Python 字符串。
> 用写文件的方式落盘再执行。
> 而且断言失败时整个文件不写入，**前面已经成功的编辑会一起回滚**，
> 很容易误判成「没改动」。

## 三·五、包来源、许可与孤儿包（触发：导入完清点素材之前）

**目的**：说清某个包**从哪来、要不要原件、升级会不会冲掉生成物**；有付费件时提前做许可决定，不留到交付。

### 依赖写法三种，都不可复现

```bash
grep -nE '"file:|git#|\.git\?path=' Packages/manifest.json
```

| 写法 | 含义 | 为什么要查 |
|---|---|---|
| `file:` | 指向工作区外目录 | 换机/移目录就打不开 |
| `git#master` | 直接引分支 | 只是 `Library/PackageCache/` 里有当年副本，删 Library 就变 |
| `.git?path=…#master` | 子目录引 git | 同上，且更隐蔽（历史核查漏过一次，实为 7 个工程不是 5 个） |

**达不到怎么办**：命中就转 VPM 版本号再继续（见第四节）；转不了的在导入报告里点名，归档时单独处理。

### 素材包说明三行

每个包记 **版本 / 下载日期 / 升级注意** 三行。永久缺件的查库规矩（先去本机 `<素材库>/`、不要让用户重下）见 [10 · 缺件怎么办](../10_接单建档.md)，此处只留指针不重复。

### 升级厂商包之前：先登记生成物

1. 把当前包**移走**（或先 `#GENERATED`/`Backup/` 登记），因为升级会覆盖同名路径。
2. 头像工具按头像生成的目录结构各异（历史实测 `#GENERATED/`、`Backup/` 两种命名，F §5）—— 都要在应用表里记一行，否则升级后分不清哪些是生成物、哪些是原件。
3. **付费原包升级为一个许可决定，不是顺手升**：厂商原件（含 Booth 付费 zip、Patreon shader）**不进交付**（K #3/#4；SOP「许可」条目 2026-09-18 核查为空，本条是首批）—— 要附、要升级都要用户点头，并写进交付说明。

### 孤儿包登记（只在 `Packages/`、不进 `manifest.json`）

**定义**：包目录在 `Packages/` 下、`manifest.json` 却没有它的条目 —— 它不参与版本解析，**换机 / `vrc-get resolve` 后会消失**。

- **判据**：`Packages/` 下目录数 vs `manifest.json` + `locked` 条目数；对不上的逐个登记。历史实测：F §2 正文列 6 种、结论表写 5 种，**7 个工程有依赖问题**（本文核，非 5 个）。
- **达不到怎么办**：孤儿包要么写进 `manifest.json` 的 `dependencies`、要么搬进 `Assets/` 并接受它不受包管理；**不要留着不管** —— 它今天能编译纯属 `Library/` 缓存还在。

## 四、依赖可复现性（归档前必查）

```bash
grep -E '"(file:|https?://)' Packages/manifest.json
```

命中就要转成 VPM 版本号 —— `file:` 本地路径和 `git#master` 分支依赖**都不可复现**：

- `file:` 指向工作区外的目录，换机器 / 改了目录就打不开（Unity 直接返回码 1）
- `git#master` 能打开只是因为 `Library/PackageCache/` 里有当年 clone 的副本，删掉 Library 就变了

**查当年真正用的版本**：读 `Library/PackageManager/ProjectCache`（文本）。

⚠ 该文件里 **`version:` 字段在 `name:` 之前**，往后找会取到相邻条目的值。

`source:` 枚举：`1=Registry 2=Builtin 3=Embedded 4=Local 5=LocalTarball 6=Git`

## 五、VPM 包的 zip 解错位置：文件全在、引用全对、编译也过，但**版本定义静默失配**

厂商发的功能插件常常是 **VPM 包的 `.zip`**（不是 `.unitypackage`），
里面带 `package.json`。这种包**必须落在 `Packages/`**，落进 `Assets/` 就只是一堆源码 ——
Unity 的包管理器不认识它，于是所有 `versionDefines` 都匹配不上。

> 证据（2026-09-09 工程C）：面捕框架的 VPM 发行包 `<框架>-v<版本>.zip`
> 被解到了 `Assets/Packages/<框架包名>/`。
> 结果面捕插件的安装目录里，那个安装器插件的 asmdef 里
> `versionDefines: [{ name: "<框架包名>", define: "<框架宏>" }]`
> 永远不成立 → 插件编译进 `#else` 分支 → 窗口只显示一句
> **"<框架名> is not detected. Please import it."**
> —— 而框架其实就在盘上，472 个资产一个不少。

**为什么难查**：这个坑**不报错**。asmdef 的 `references`（按 GUID）照样解析得到，
编译零错误，控制台干干净净。唯一的表现是一句「检测不到」的人话提示，
读起来像「你没装」，于是第一反应是去装 —— 方向就错了。

⚠ 反过来也成立：**`versionDefines` 的 `name` 只认包管理器注册的包**
（`Packages/` 下的内嵌包、VPM 包、Unity 注册表包都算），不认 `Assets/` 里的任何目录。
所以判据是「Package Manager 里有没有它」，不是「文件在不在」。

#### 判据（三条，成对给出正反两面）
1. **编译产物**里有没有那个 define 才算数，`.csproj` 不算 ——
   `.csproj` 只在**脚本变动**时才重新生成，包位置变了它不动，会给出过期的假答案。
   查 `Library/ScriptAssemblies/<插件>.dll`，二进制里搜：
   - `#if` 分支独有的类型名（如基类 `FaceTrackingInstaller`）→ **必须命中**
   - `#else` 分支独有的符号（如那个分支才有的字段 `addonConfig`）→ **必须不命中**
   只查前者会被「两个分支都引用的通用符号」骗到（例如 `EditorWindow` 两边都在）。
2. **搬迁不能断引用**：搬之前先把「消费方指向包内的 GUID 集合」存成基线，
   搬完比对集合**完全一致**。判据不是「文件还在」——文件在而 GUID 变了，
   引用会静默变 null，编辑期不报错。连 `.meta` 一起搬就不会变。
3. 顶层包目录搬进 `Packages/` 后，**它自己的 `.meta` 要删掉**（包根不需要 meta）。

#### 做法与代价
关掉 Unity 再搬。`Packages/` 下的内嵌包**只在启动时扫描**，
开着 Unity 搬完不重启，define 不会生效 —— 会得到「搬了没用」的错误结论。
代价是一次全量重导入（本次 472 个资产，约 3 分钟），换来的是 GUID 与包注册都干净。

**不要退而求其次去手工加 Scripting Define Symbols**：那样 define 与包的存在**解耦**了，
包一旦被移除或换版本，define 还在，插件会编译失败或者更糟 —— 编译过了但行为不对。

## 补充

- **补救时按原始 GUID 写盘**：`unpack_unitypackage.py --only-new-guids` 只解工程里还没有的 GUID，公共资产不重复写，避免同 GUID 两个路径。
- **0 引用 ≠ 漏用**（2026-09-19 验收 BP）：写「导入了没用上」之前先 grep 工程里已有的方案文档（`_配色方案.md`、`_素材应用表.md`）——工程B挑染包 Ↄiao2 是配色方案里明确不用的。
- **查「素材里有没有 X」连 zip 原清单一起查**（`unzip -l`）：解出的目录可能不全，聊天截图/需求表常根本没进素材包（2026-09-19 工程C查面捕设备）。
