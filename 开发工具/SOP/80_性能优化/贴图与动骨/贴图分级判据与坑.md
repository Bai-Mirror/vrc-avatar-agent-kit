# 贴图分级：判据、工具与六个坑

> 从 [`80_性能优化/贴图与动骨.md`](../贴图与动骨.md) 拆出的子页。接手自「先用工具出方案」与「贴图分级：三个必踩的坑」两节；格式与尺寸的查法、红线与 A/B 仍留主页。

## 先用工具出方案：`通用工具/tex_tier_plan.py`

```bash
python 开发工具/通用工具/tex_tier_plan.py <工程目录> [--csv out.csv]
```

不开 Unity，走 **场景 → 预制体 → 材质 → 贴图 → .meta** 的纯文本链路，
按 shader 属性判档，输出逐张的「现在→目标」清单。只出方案不改文件。

### ⚠ 这个脚本踩平的三个判据坑（2026-09-09，都是我先做错再改对的）

**① `maxTextureSize` 是上限，不是实际尺寸。**
一张 512 的源图设了 2048 上限，占的显存还是 512。按上限估算**虚报 7 倍**
（估 1107 MB / 烘焙体实测 160.7 MB）。必须读图像文件头拿真实尺寸，
再取 `min(源图长边, 导入上限)`。读不出尺寸的（exr/hdr/tga）标问号，别拿上限顶替。

**② 只看场景 YAML 里直接出现的 GUID 会严重漏。**
预制体实例上的材质挂在 `.prefab` 里，场景只引用预制体 ——
不做传递闭包，工程C只找到 10 个材质，而实际有 79 个。必须展开 prefab/controller/asset。

**③ 就算修对了①②，总量仍然只是上界，不能当预期收益。**
闭包会把构建后被 AAO 剔掉的材质算进来，压缩格式也只能假设。
**真实收益只有一个判据：改完重跑 `PerfReport.cs` 对比前后。**
逐张建议是可靠的（按属性判档与总量无关），总量数字不要拿去汇报。
## 贴图分级：三个必踩的坑（2026-09-01 实测）

### ① 判「是不是主图」要用**白名单**，不能用 aux 黑名单

lilToon 的辅助贴图属性有几十个（`_RimColorTex` / `_MetallicGlossMap` /
`_ReflectionColorTex` / `_Bump2ndScaleMask` / `_MatcapBlendMask` …），黑名单必然漏。
漏掉的那几张会被当成主图给 2048 档，而厂商原本把它们设成了 512 ——
**一抬就是 16 倍内存**，实测贴图内存从 102.6 反涨到 139.9 MB。

正解：`MainProps = { _MainTex, _Main2ndTex, _Main3rdTex, _BaseMap, _BaseColorMap, _Albedo }`，
不在这个白名单里的属性一律当辅助图。

### ② 按**着色器属性**判，不要按文件名

Kitty 的法线图文件名只是一个编号 —— 名字里没有 normal，按文件名判会当成主图。要看材质把它挂在哪个槽（`_BumpMap` 等）和导入类型。
它挂在 `_BumpMap` 上，按属性判一目了然。文件名只当兜底。

### ③ 只有点名的才允许**抬高**，其余一律只降不升

A/B 之后要把某张图从 512 收回 1024 时必须能抬；但无差别双向设会把厂商刻意压低的图全抬上去。
界线：`Explicit` 表里点名的双向设，其余 `if (current > want)` 才改。
- **改 TextureImporter 必须 `SaveAndReimport()`**，只 `SetDirty`＋`Refresh` 不落盘；原设置在改前备份，已有备份不覆盖。分档用 `tex_tier_plan.py`/`tex_tier_apply.py` 按shader属性判用途，改.meta后重导并读回；旧 `TexOptimize.cs` 只作压缩格式参考，不复用其按文件名分档逻辑。
