# 内存预算与并发（2026-09-22 OOM 事故）

**事故**：09-22 20:28 内核 OOM 杀掉 Claude app 所在的整个 systemd scope（`app-com.anthropic.Claude-*.scope`，峰值 22.3 GB 内存＋5.6 GB swap）。**从 Claude 会话里起的一切都在这个 scope 里**：两台交互 Unity、一个批处理导入 Unity、后台 Blender、约 9 个 DSH 会话（3 个 H-05 还在各自嵌套开视觉会话）＋每个 DSH 自带的 MCP 子进程——全部一起死，Claude 本身也被重启。代价：DSH 产出写完未提交、Unity 编辑器与导入队列中断、影子凭据留在临时目录。
本机总内存 30 GB（`free -g`；旧文档写的 14 GB 是迁机前的）。

## 可查问句（派工／起重进程之前）
1. `free -g` 的 available 还有多少？**低于 8 GB 不再起新的 DSH 会话或批处理 Unity。**
2. 现在有几个 DSH 会话？`pgrep -fc "bin.js --profile headless"`（嵌套视觉会话也算）。**同时 ≤4 个。**
3. 开着几台交互 Unity？**两台都开时不跑批处理导入**；批处理导入与交互 Unity 合计 ≤2 个 Unity 进程。
4. 要派的是不是「会嵌套开会话」的活（部件图鉴盲标、多路 agy）？这类**一次只派 1 个**。

**结构闸门**：`dsh_task.js` 派工前自动查（available <8 GB 或 DSH 会话 ≥4 就每 30 s 等一次，最多 90 min；`DSH_TASK_MIN_GB`/`DSH_TASK_MAX_SESS` 调阈值，`DSH_TASK_NO_GATE=1` 关）。嵌套派工在沙箱里看不到别的会话，只有内存那条生效。

## 启动与恢复走脚本（2026-09-23 工作流审理 B4/A6，用户拍板）
- **起 Unity 一律 `bash 开发工具/通用工具/unity_run.sh --project <工程> [--batch --method X]`**：查内存（交互 ≥8 GB、批处理 ≥6 GB）、同工程已有活进程就拒绝、`-force-vulkan`、进程挂 `systemd-run --user` 单元带 `MemoryMax`（交互 14G、批处理 10G，`--mem` 调），超限只死这个 Unity，不再拖垮整个 Claude 进程组；批处理全机一把 flock 串行。
- **完整构建与 NDMF/VRCFury 预处理不在交互编辑器里跑**：4 次同一 Vulkan 交换链崩溃栈都来自交互编辑器弹进度条；改 `--batch --method <入口>`（`-executeMethod`），交互编辑器只做看与改。
- **崩溃后 `bash 开发工具/通用工具/unity_recover.sh <工程>`**：只报告（进程、日志尾、锁、MCP 状态、未提交改动）；进程还在就退出码 1 并提示先 kill；`--yes` 才清陈旧锁；`--launch` 再经 unity_run.sh 重开。绝不自动存盘、不 checkout。
- **DSH 并发**：`dsh_task.js` 除了 pgrep 还按 `<工作区>/.dsh_slots/` 槽位文件计数（嵌套派工在沙箱里看不到进程，但看得到槽位；实测嵌套视觉会话也会落槽位）。**DSH 会话不挂 MemoryMax**：`spawnSync` 超时只杀直接子进程，`systemd-run --scope` 一层会留下孤儿；单会话 0.3–0.8 GB，靠槽位数（≤4）控总量。取舍：OOM 的主犯是 Unity（3–8 GB/台），先把它关进 cgroup。

## 取舍
- 并发数不是按 CPU 定的，是按内存：一台交互 Unity 约 3–5 GB，批处理导入 2–4 GB（大工程更多），一个 DSH 会话连 MCP 子进程约 0.3–0.8 GB，Claude app 1–2 GB。
- 宁可排队：H-05 这类 12 套图鉴按「一次 1–2 套」串行跑，比并发 3 套再被 OOM 全部打回划算。
- 事故后恢复清单：删各工程 `Temp/UnityLockfile`、`~/.unity-mcp/unity-mcp-status-*.json`、`~/.dsh/handoff.lock`（持有者 pid 已死时）；**找 `_dsh_tmp*/**/.dsh/.credentials*` 删掉影子凭据**；逐个查被杀任务的产出是否已完整（JSON 字段、渲图）再决定代落记录还是重派。

## 看门狗（09-22 起常驻，09-23 改 v2）
- 做法：每 10 s 读 `MemAvailable`，< 3 GB 就 `kill` **批处理** Unity（最不要紧、可重跑），保交互编辑器与 DSH。
- **匹配必须锚定可执行文件路径**：`pgrep -f '^<Unity安装根>/Editors/[^ ]+/Editor/Unity -batchmode'`。v1 用不锚定的 `pgrep -f "Editor/Unity -batchmode"`，09-23 01:56 把「启动它的那条 shell」（命令行里带着脚本全文）当成目标杀了——任何命令行里恰好含这段文字的 shell 都会中枪。
- 脚本写成文件再 `bash 文件` 起，别用 heredoc 写完同一条命令里直接跑（父 shell 命令行会带着匹配串）。
- 09-23 01:56 实况：交互 Unity 7.8 GB（DSH 在里面跑完整预处理）＋ MeteorLens 批处理 Unity 5.1 GB ＋ 用户的安卓模拟器 1.5 GB（systemd 用户服务起的，不归我们管）→ 可用 1 GB。起批处理前的「≥8 GB」只看起点，交互编辑器里的预处理会再涨 2–3 GB；**交互编辑器在跑完整预处理时别起批处理**。

## 前一次：Unity ＋ 用户的 Blender 同开时，别再并发无头 Blender（2026-09-20 23:53，从「进程与等待」并入）

**触发时刻**：一边开着 Unity、用户那边还开着 Blender，我又要跑 `blender --background` 做测量/渲染。

**这次的现场**：本机 30 GiB 内存被打到 **22 GiB 已用 / 1.7 GiB 可用，swap 13/15 GiB**。
占用榜：Unity RSS **4.4 GB**（托管 1.6 GB / 保留 2.3 GB）、qemu 虚拟机 2.5 GB、**opencode ×3 约 1.8 GB**、
claude-desktop ×2 约 1.1 GB、用户的 Blender RSS 450 MB 但**换出到 swap 1.99 GB**。
后果：**Claude 桌面端被重启**（journal：`Started app-com.anthropic.Claude-…scope`，
旧实例 `1.1G memory peak, 583.4M memory swap peak`），随后一个辅助进程报
`Missing X server or $DISPLAY … The platform failed to initialize. Exiting.`。
**Unity 自始至终没崩**（无 `mono_crash*.blob`、MCP 秒回、日志里只有正常的 Asset Pipeline Refresh）——
看起来像崩溃，其实是全机在换页。

**每个无头 Blender 都要完整加载 .blend**：工程B这份 135 MB 的场景，一个无头实例就是 GB 级。
我这一轮连开了 6 次（修复扫参、烘焙、闭眼、导出、渲图 ×2）。

**做法**：
- 开工前 `free -h`；**swap 用掉一半以上就先清场再干活**。
- 无头 Blender **串行、跑完即退**，别 `run_in_background` 挂着并发。
- 能在**已经开着的** Blender 会话里用 MCP 只读测量的，就别另起无头实例（测量类几乎都可以）。
- 要清场时，**用户的 Blender/Unity 不能由我关**（可能有未存盘改动，见「绝不擅自丢弃场景改动」）；
  先把可关的（虚拟机、闲置的 opencode 会话）列给用户，由人决定。
