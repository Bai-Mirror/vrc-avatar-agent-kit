# 杀进程、找进程、等进程

这页解决的问题：**在本机用 bash 管 Unity/Blender/脚本进程时，三个反复踩到的坑**，以及 Unity 的 GTK 窗口重排崩溃。
内存不够时的并发与清场 → [内存预算与并发](内存预算与并发.md)。

**别在同一条 bash 命令里用 `pkill -f <串>`**（2026-09-18 两次、09-20 第三次把自己的 shell 杀掉，退出码 144）：`-f` 匹配整条命令行，而这条命令本身就含那个串。改用 `pgrep -f <串>` 列出 PID，排除 `$$` 后逐个 `kill`；Unity 用 `pgrep -x Unity`。同理，**等进程结束的 `until ! pgrep -f <串>` 也会匹配到等待循环自己**，永远等不完（2026-09-18 空等 10 分钟）：用 `pgrep -f <串> | grep -v $$` 之外，更稳的是让被等的命令自己 `run_in_background`，完成时自动通知。

> **第三次是怎么犯的（09-20）**：规则记得住，栽的是**触发时刻** —— 当时在改一个跑太久的脚本，顺手写成「`pkill -f 脚本名` ; 打补丁 ; 重跑」一条复合命令，注意力在补丁上，没意识到这条命令行自己就含脚本名。
> **可查问句**：我这条命令里有没有 `pkill -f`？有的话，`-f` 后面那个串是不是也出现在这条命令的别处？

> **`pgrep` 的模式是 ERE，`\|` 不是「或」（2026-09-20）**：写 `pgrep -a -f "Unity.*工程B\|Unity/Editor"` 时，
> `\|` 在 ERE 里是**字面竖线**，整条当成一个字符串匹配 → 返回空 → 我据此判断「Unity 没在跑」。
> 后果：删掉 `Temp/UnityLockfile` 又起了第二个编辑器，**同一个工程上同时跑了两个 Unity**（有损坏 Library 的风险）。
> **写法**：多模式用 `pgrep -f 'A|B'`（不转义）或干脆 `pgrep -x Unity` 只按进程名。
> **更重要的是判据**：起 Unity 前先 `pgrep -x Unity` + `ps -o pid,lstart,args`，**看到 lockfile 就说明有人在用，别删它**——
> lockfile 存在本身就是「已有实例」的证据，删掉它等于把 Unity 的互斥保护拆了。

> **`read -t N < /dev/zero` 不会等待（2026-09-20）**：`/dev/zero` 永远立刻有数据，`read` 马上返回，
> 写成轮询循环就是空转 —— 我的「等 Unity 退出」循环 12 次瞬间跑完，误报「还在跑」。
> 前台 `sleep` 在本环境被禁；**要等就让被等的命令 `run_in_background`**，完成时自动通知；
> 非要在脚本里等，用 `python3 -c "import time;time.sleep(1)"`。


**GLib-GIO-CRITICAL `g_dbus_proxy_call_sync_internal` 是无害噪音**，Unity 在 Linux 下每隔几分钟就报一次，别当故障线索。


## Unity 崩溃签名之二：GTK 窗口重排死锁（2026-09-21 00:53）

**现象**：Unity 在**无人操作时**自己退出，工程目录留下 `mono_crash.mem.<pid>.1.blob`。
`~/.config/unity3d/Editor.log` 末尾是 gdb 栈 ＋ `Exiting early due to double fault.`

**栈的形状（认这个）**：
```
ContainerWindow_CUSTOM_set_Internal_Position_Injected   ← C# 侧设窗口位置
  → ContainerWindow::SetRect → SetGtkWindowSizeAndPositionSync
  → PumpGtkMainloop → gtk_main_do_event → OnConfigure
  → GUIView::ReshapeIfNeeded → ThreadedWindow::Reshape
  → GfxDeviceClient::WindowReshape → Semaphore::WaitForSignal   ← 主线程卡在等渲染线程
```
**与已记的另一种崩溃要分开**：那一种落在 `libnvidia-glcore`、发生在**反复进出 Play** 时；
这一种落在 **GTK 窗口重排**，与 Play 无关，触发点是窗口尺寸/位置被改（桌面环境动了窗口、
X 会话有变动、或编辑器恢复布局）。同一轮里 journal 还出现过
`Missing X server or $DISPLAY … The platform failed to initialize.`，提示 X 侧当时确有异动。

**真因（2026-09-21 01:00 查实，不是随机事件）**：本机图形会话是 **xrdp**（`Xorg :10 -config xrdp/xorg.conf`，WM 是 `kwin_x11`）。
`~/.xorgxrdp.10.log` 里能看到 **`screen resized to 2560x1600` → 后来又 `resized to 3840x2160`**（RDP 客户端换了分辨率/重连）。
而 Unity 把主窗口矩形存在 `~/.local/share/unity3d/prefs` 的 `RestoredMainWindowSizeX/Y/W/H`，
当时存的是 **0,115,2560×1485 —— 宽度正好等于旧屏宽**，即「铺满旧屏」。
启动时把这个矩形同步给 kwin，在 xrdp 下协商不收敛 → 主线程卡在 `WaitForGtkEvent` 等渲染线程 → double fault。
**所以它会稳定复现**：崩一次之后每次重开都在同一处崩，不是运气问题。

**修法（实测一次见效）**：备份后改 `~/.local/share/unity3d/prefs`：
`RestoredMainWindowSizeX/Y/W/H` 改成明显不贴边的值（如 120,120,1800×1100）、`IsMainWindowMaximized=0`；
顺带把 `MCPForUnity.Editor.Windows.*x/y` 也挪离原点。改完重开 → `MCP_READY after 5s`。

> **判据**：`RestoredMainWindowSizeW` 是不是**恰好等于某个历史屏幕宽**？是就说明它铺满的是一块已经不存在的屏。
> 另：认证/登录类窗口也是由 C# 设位置弹出的（栈顶就是 `ContainerWindow_CUSTOM_set_Internal_Position_Injected`），
> **在 RDP 改分辨率或刚重连之后别立刻弹这类窗口**。

**处理**：
1. **先看 git**：这类崩溃不损坏资产。`git status <工程>` 干净就说明盘上与提交一致，没丢东西。
2. 清 `mono_crash*.blob`（每个 10 MB）与 `Temp/UnityLockfile`，删 `~/.unity-mcp/unity-mcp-status-*.json`；
   **崩溃日志先另存一份**再清空 `Editor.log`，否则下次启动会被覆盖、查不到栈。
3. 带 `-force-vulkan` 重开（本机既有惯例）。
4. **重开前必须 `pgrep -x Unity` 确认没有活着的实例**，见本页上一条。

> **可查问句**：Unity 是「我操作时崩的」还是「自己崩的」？自己崩的先去 `Editor.log` 末尾找栈的形状，
> 别默认是上次那个原因。
