## 一、对外口径：**9 种**

对外统一说「情景有 **9 种**」，即 schema 的依赖种类 D1–D8（`01_需求说明.md:44-53`；D6 同时管乳头键与脚甲显隐）：

| 依赖 | 情景一句话 |
|---|---|
| D1 | 身体 ← 衣物：覆盖件可见就写身体收缩／删除，脱下恢复 |
| D2 | 脚 ← 鞋：按鞋跟选脚型姿态键（平／中／高跟是取值） |
| D3 | 袜 ↔ 脚型；袜 ← 鞋：袜可见时脚型满足袜，鞋关袜开不回中性 |
| D4a | 衣物 ← 衣物：外层可见时内层收缩，外层关回基线，**再开要重新收缩** |
| D4b | 内衣 ↔ 下装：谁缩谁、谁压谁显隐、同部位优先级链 |
| D5 | 衣物 ← 体型：贴身件跟随胸／臀／腿滑块，变体按体型选 |
| D6 | 遮挡显隐：任一覆盖件可见即隐藏（乳头键、脚甲） |
| D7 | 发型 ← 外套、帽：取目标值，关闭回基线 |
| D8 | 姿势相关：走、坐、蹲不穿出（本期只管蒙皮驱动部位，裙摆归视觉残余） |

## 三、使用取舍

- **对外/需求/验收表**用 9 种（D1–D8）；**内部复核、找漏**用 12＋4，因为 D6 一个依赖同时管乳头键（类 D）与脚甲显隐（类 V2），D1 同时管收缩（A1）与删顶点属性，对不上粒度。
- **F 类（配件→脸部键）在 9 种里没有对应**，是复核时补的（工程G、工程F都没复现，客户反馈细节缺；`scnV.md:154`）。要进 schema 需先补一个依赖种类，别硬塞进 D6。
- **C2／C3 没有干净的单一 D 归属**：C2 的腰由衣服收缩驱动（同脚型类），C3 是基线锁定与厂商滑块抢键；归类时按「触发源」不按「部位」（`scnV.md:124-125`）。
- **实例总数没有可用口径**：`critic.md:11` 写时 14 个历史工程还没扫过；09-19 E-T11-01 已用 T-11 静态规则扫过（`_长程任务_20260918/审查产出/_历史工程/静态规则候选_20260919.md`，每工程 0–71 条候选），但那是**候选、不判对错**，没有几何/构建期/人判复核。所以「扫出多少种情景」仍只答 9 种/12＋4 类，实例总数要等复核后再给。
- 触发问句：*这个情景在 schema 里靠哪个依赖表达？对不上时是改归类还是补依赖？* 取舍：宁可多一列复核类，不要为凑 9 种把 F、C2、C3 硬塞。
