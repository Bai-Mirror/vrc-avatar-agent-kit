# 路线选择与审美校准

2026-09-07 工程B_Milfy 单的实测结论。**推翻了本规程原来「路线 1 可选」的写法。**

## 一 · 路线 1（不出 Blender）**不成立**，默认走路线 2

原来的说法是：在 Unity 侧给 SkinnedMeshRenderer 设 blendShape 权重、构建期用
**AAO FreezeBlendShape** 烘焙，这样 FBX 一个字节不动、面捕的 sha256 校验能过。
**两个前提都是错的。**

### ① AAO Freeze 不做闭眼补偿，而捏了眼睛就必须补偿

AAO 烘焙 = `新基础 = 基础 + delta×权重`，然后删掉那条键，
**其余 600 多条表情键的 delta 原封不动**。`eye_blink_1` 的位移量是按**原始**眼睑位置算的，
一旦捏脸把眼睛放大或上睑抬高，闭眼就闭不拢。

实测（Blender 量闭眼状态下上下睑缘最近距离）：

| | 睁眼眼裂 | 闭眼残留 |
|---|---:|---:|
| 素体默认 | 16.65 mm | **7.37**（判据零点） |
| 捏完（24 条） | 19.17 | **8.76 ＝ +18.8%** |

**主要肇事者是 `face_eye_big` / `face_eye_height_up` 这类脸型键**（放大眼睛），不是眼睑键。
→ 只要动了眼睛大小就得补偿，而补偿只能在 Blender 做。

### ② 「改了 FBX 就装不了 Triturbo 面捕」是错的

`FaceTrackingInstaller.cs:167` 的注释原文：

```csharp
//we can not find the version by sha256
//=> user do edit on the fbx
```

**厂商专门为「用户改过 FBX」设计了 fork 流程**：sha256 失配时弹版本下拉问「从哪个原版 fork 的」，
内部 id 记成 `{版本}_fork`，再选目标 `original` / `current_in_use`。
**失配是入口，不是阻断。**

两条目标路径的差别（`BlendShapeAppender.cs`）：

| 路径 | 行号 | 校验 | 用途 |
|---|---|---|---|
| `original` | 141-151 | 查顶点数 + `m_VerticesHash`，对不上 `return null` | **只对未改动网格有效** |
| `current_in_use` | 450-472 | 按控制点索引直接写 channel，**不查顶点数也不查 hash** | fork 路径 |

→ **走 fork 必须用 `current_in_use`，而它零校验。**
所以「重导出的 FBX 顶点数与索引顺序必须与原版一致」得**我们自己验**，工具不会报错。
把这一条加进 30b 步骤 5 的二进制自检里。

## 二 · 允许一条例外：**闭式变换的自定义键**

页首硬规矩禁的是「AI 凭手感雕顶点」，不是「按闭式公式算位移」。
当**厂商键里确实没有对应方向**（要有实测证据）**且用户明确点头**时，可以建自定义键。

本单的实例：外眼角要「转平」，而厂商没有可用的旋转键 ——
`eyelid_corner_rotate_down` 只有 **18 个顶点**，拉到 400 也几乎看不出，还削上睑弓度 2.06~2.79 mm；
`face_eye_height_up/down` 主要在改眼裂（20.57→14.92）。厂商键压外眼角上扬的天花板是 **−13%**。
自建键做到 **−36%**。

### 建这种键的四条规矩

1. **必须是闭式变换**（旋转/缩放/平移 + 掩膜），写得出公式，不是逐顶点手调。
2. **叠层卡片素体要选对轴。** Milfy 的眼睛是几十张 0.03 mm 间距的叠层卡片。
   绕**深度轴**的面内旋转，位移的深度分量恒为 0 → 层间距零变化；
   **绕其他任何轴转都会搅乱叠序**，直接 z-fighting。
3. **位移要按「建键那一刻的混合形状」算**：`新键位移 = R(当前混合) − 当前混合`，
   这样其余键全开时结果才是当前脸的精确变换。**用户改完别的键后要重建一次。**
4. **验收两条**：① 受影响顶点有多少落在掩膜满强度区内（本单睑缘 89.5% 在内、0 个在外）；
   ② 拿**不受采样漂移影响**的判据验功能没坏（本单：闭眼时上睑顶点到最近下睑顶点的距离，
   旋转 0/1/2 三档为 8.699/8.667/8.907 mm，±2.4%）。

⚠ **别用会跟着变形漂移的判据。** 本单我先用「按未变形位置定的采样列」量闭合，
得出「旋转让闭眼残留从 6.13 涨到 6.62」的假结论 —— 其实是顶点转出了采样列。

## 三 · 审美校准：**开局别从天花板起手**

本单最大的效率损失：我开局把每个轴都给满（child 1.0、cheek_puku 1.0、三条放大键 1.0），
用户**每一条都往回砍**，来回十几轮。更糟的是那组放大键被焊进了之后 11 轮的基线，
眼形 sweep 我只往上探（到 1.3）**从没往下试过**，最后用户自己砍了 83%。

**分轴起手，两个方向反着来**（依据见 `<订单>/_捏脸审美校准.md`）：

| 轴 | 起手 |
|---|---|
| **放大类**（`face_eye_big` / `face_eye_height_up` / `face_child`） | **从弱起**（0.15~0.30） |
| **弧度类**（`eyelid_center_up` / `eyelid_corner_wide_1` / `lower_eyelid_flat`） | **从满档甚至外推起**（1.0~1.5） |

把用户的审美关键词记下来作为校准依据：写成**几何画像**（可跨素体迁移，键值不可），而不是键值清单。

## 四 · 反推审美要看「差」，不是看终值

**信号最强的是「AI 给满、用户砍掉」的那些键。**
典型形态：AI 把某个放大类键给满，用户大幅砍掉、同时自己加了另一个相关键 —— 这类差值直接说明偏好（例如要放大 A 不要放大 B）；最终数值以用户拍板为准，记录在施工记录里。这条只看最终值看不出来，只有对着「提案 vs 定稿」的差才读得到。

**所以用户的原话要留档。** 本单子代理写校准文档时指出「原话只在任务书里、项目文档无留存」——
后来单独建了 `_捏脸决策原话.md`。**逐轮决策与原话是审美反推的证据基础，会话结束就没了。**
