# 形态键烘焙与表情补偿的细节

这页解决的问题：用户**直接把几十个形态键拉到某个值**这一型捏脸，怎么把它烤进基础网格而不破坏表情。
步骤与判据在主页的确定化步骤表，这里是每一步的做法细节。

SOP 前半段讲的是**几何缩放型**捏脸（整组做相似变换）。更常见的另一种是
**用户直接把几十个形态键拉到某个值**——这一型的处理完全不同，流程如下。

| # | 步 | 判据 |
|---|---|---|
| 1 | 留三个还原点 | `*_unity_original.fbx`（覆盖前的 FBX）、`*_sculpted_prebake.blend`（捏完未烤）、`*_baked.blend`（烤了未补偿） |
| 2 | 清点要烤的键 | 非零且**不是我自己设的**（例如我为了效果设的 `pupil_off` 就该排除，烤进去以后再被动画推到 100 会双重应用） |
| 3 | 精确重建式烘焙 | 见本页下文。**验收：`Basis` 与 `mesh.vertices` 最大差 = 0mm** |
| 4 | 闭眼补偿 | 见下 |
| 5 | 全量形态键检查 | `shapekey_audit.py`，见下 |
| 6 | 还原材质槽 → 导出 → 二进制自检 | 见下「材质槽陷阱」 |
| 7 | 覆盖 FBX → **重挂材质 + 扫空槽** → 实机渲染 | 见下 |

### 闭眼补偿要分左右眼

记忆里的公式 `新键 = 新Basis + 原始位移 − ratio × eyemask × d` 是对的，但**系数与掩膜都必须按眼分**：
单眼键（`blink_L` / `ウィンク`）的闭合度是两眼平均后的稀释值，用对称掩膜会把**没闭那只眼**的捏脸一起撤销。
做法：上睑簇按 x 正负分两簇 → 各求质心当眼心 → 各建一个 30mm 满 / 50mm 零的 smoothstep 掩膜 → 各算各的 ratio。

**闭合度怎么定**：有的素体 `blink` 只推上睑、下睑完全不动（輝夜就是，1166 个点全部向下）。
这种情况下记忆里「上睑下移 + 下睑上移」的定义取不到下睑，退化成「上睑簇的平均下移量」即可。

Blender 形状键存绝对坐标、Unity BlendShape 存相对 delta，两侧补偿需求方向相反（Unity 改基础网格天然有效，闭合类表情才要补偿）。

闭眼补偿要加性抵消（`新delta = 旧delta − c·W·S`），不是乘性放大；判据用眼球露出率（射线遮挡），不是眼睑收敛度（2026-09-08 纠正）。

### 全量形态键检查（烘焙后必做）

```bash
python 开发工具/通用工具/shapekey_audit.py <工程目录> --baked <烘焙清单.json>
```

烘焙清单是 `{键名: 烘焙权重0-100}`。工具遍历全工程 `.anim`，对每条 `blendShape.X` 取峰值，
加上烘焙量，>100 即外推越界。输出还包含「静息表情里写了被烤的键」（双重叠加）与
「被烤但无动画驱动」（安全）两张表。

> 结果可能是**零越界**——輝夜这单 1431 个 clip 里，被烤的 46 个键一个都没被驱动。
> 那就不要为了"做点什么"去改动画。查过、确认没有，本身就是产出。

### 越界扫描范围与「游戏里会被钳制」（触发：把外推值留在交付件里之前）

**扫描源不止 `.anim`**，还要覆盖：

- **MA ShapeChanger 的 Set 值**（历史实测有工程用 Set 写脸部数值、也有脚部 Set 60，面板数值 ≠ 实际效果）
- **场景 / prefab 的 `m_BlendShapeWeights`**（烘焙默认值也在这里，P1/2 有非零默认权重）

> **补充（2026-09-21 实测）**：不止进 Play——**在编辑模式下调用 `nadena.dev.ndmf.AvatarProcessor.ProcessAvatar(clone)`
> 做构建验证，同样会把 `legacyClampBlendShapeWeights` 置 1，而且不会像退出 Play 那样自动还原**。
> 我这轮跑了 4 次 ProcessAvatar，收工时 `git status` 才发现 ProjectSettings 脏了。
> **可查问句**：这轮我跑过 ProcessAvatar / 进过 Play 吗？跑过就 `git diff ProjectSettings/` 看一眼，
> 是副作用就 `git checkout --` 还原，别提交。

> ⚠ **待证伪（E-未核-08）**：`legacyClamp`（`PlayerSettings.legacyClampBlendShapeWeights`）在**没有 AAO 的工程**里编辑模式是否恒为 1、Play 被强杀后会不会把 1 留盘上、`GetBlendShapeWeight()` 返回截断前还是后 —— **都没实证**（`G_legacyClamp结论.md`，2026-09-18 只查了 工程A）。**先不要把它当定论用。**
> **已确证的只有**：装了 AAO 且 Enabled 时，编辑模式钳制位 = 0（能预览外推）、Play = 1（与 VRChat 客户端一致）；客户端把形态键钳在 0–100（SDK 3.5.1 release notes）。

- **审查项**：凡是把 >100 / <0 的外推值留在交付件里，先问「Play 口径（`legacyClamp`=1）下它长什么样」——**在 Play 里渲图判定**，别拿编辑模式预览当客户端效果。
- **取舍**：外推是免费拿反向形变的好手段，代价是「编辑器里好看、客户端看不到超出部分」；两侧不对称，所以至少要把越界条数列出来并逐条判定，**达不到就退到 100 上限内的方案**，不要靠「应该没事」。

### 删键后「按索引」的权重覆盖：写 0 的那几条别顺手还原（2026-09-19 工程B）
- **触发**：烘焙删了形态键（工程B 668→644 条）后，清理场景里 `m_BlendShapeWeights.Array.data[N]` 这类按**索引**写的 prefab 覆盖时。
- **问**：「源 prefab 在这个索引上的值是多少？」——厂商 prefab 的默认权重也是按索引存的，删键后同一索引指到**别的键**上。
- 实例：工程B场景里剩 2 条覆盖（448、498 都写 0）。还原后变成 `mouth_〇=70`、`tooth_yaeba_short_R=45`——正是厂商出厂的 `mouth_Λ=70`、`mouth_narrow=45` 错位落到新索引上；那两条 0 覆盖是**故意压住错位默认值**的，已恢复。
- **做法**：还原前逐条读 `PrefabUtility.GetCorrespondingObjectFromSource(smr).GetBlendShapeWeight(N)`；源值非 0 的保留 0 覆盖（或改 prefab 源）。验收＝脸网格全部权重为 0（或等于定稿值），而不是「覆盖条数为 0」。

## 验收（用数字，不靠眼睛）

| 指标 | 阈值 | 怎么算 |
|---|---|---|
| 接缝裂开 | 变换后不应显著变大 | 原本 <0.3 mm 的跨卡片顶点对，量变换后距离 |
| 深度变化 | `\|Δy\|` 最大值 < 2 mm | 超了就可能穿出脸皮 |
| 表情外推 | 曲线峰值 + 烘焙量 ≤ 100 | 遍历全工程 `.anim`；修法是把写入值改成 `100 − 烘焙量`，多关键帧的整条按比例缩 |

**导出 FBX 后必须做二进制自检**：`UnitScaleFactor` / `LimbNode` / `PoseNode` / `BlendShapeChannel`
等计数与厂商原版比对。**静态校验拦不住绑定姿势损坏** —— 这一单为此回滚过一次。

## 导出与自检的坑

### 材质槽陷阱（我踩过，用户一眼看出来）

**导出前必须把材质槽还原成厂商原样。** 为了在 Blender 里看清脸而临时换上的自建材质，
一旦跟着导出，Unity 侧的材质数组就会错位——輝夜这次是把 Body 三个槽换成两个自建材质，
结果**脸用上了眼睛材质**。原材质数据块通常还躺在 `bpy.data.materials` 里，指回去就行。

二进制自检要加一项：**厂商材质名的出现次数与原版相等**。
错误版本里 `Model` 节点数也会差（1986 vs 原版 1987），因为槽被并掉了一个。

覆盖 FBX 之后**必定**要做的两件事（换 FBX 会重置场景里渲染器的 `sharedMaterials`）：
重跑所有「挂材质」的工具、跑一遍空材质槽扫描。

FBX 导出两个必改参数：`apply_scale_options='FBX_SCALE_UNITS'`（默认 `FBX_SCALE_NONE` 是头号杀手）、`mesh_smooth_type='OFF'`；`add_leaf_bones` operator 默认 True，必须显式关。

覆盖 FBX 时 Unity 侧 `.meta` 一个字段都不要改，只覆盖 `.fbx` 本体；不要在 Blender 里复制或重命名材质（会多出 `.001` 材质）。

文件大小不是可靠哨兵（成功品 26.3MB 与原版 16.5MB 都正常），要用二进制自检。
