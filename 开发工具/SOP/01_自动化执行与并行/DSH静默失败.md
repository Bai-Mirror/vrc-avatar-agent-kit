# DSH 的静默失败（六条）

> 从 [DSH派工](DSH派工.md) 下沉。**共同点：都不报错**，产出看起来完全正常，
> 所以靠「跑通了没有」判断不出来，必须靠事后核验。`dsh_task.js` 已把六条都做成自动判据或直接修掉。
> 另：DSH bash 沙箱里的 `/tmp` 每条命令都是新的空目录，写进去的东西下一条就没了、它还会照样报 PASS → [沙箱限制](DSH能力与改造/沙箱限制.md) 第 3 条。

## ① 非视觉别名收到图片会编答案

**症状**：完全正常的一段回答，数字具体、格式规整，**全是编的**。

**实测**（2026-09-08，`deepseek-v4-flash`）：
- 喂一张 23 个圆点的图让它数 → 答 **22**（像模像样地错）
- 喂六个已知 hex 的色块让它读 → 六个 hex **全部编造**（与真值毫无关系）
- 两次调用的 `prompt_tokens` 分别是 **20 和 42** —— 图根本没进请求

**机制**：DeepSeek 的非视觉模型对 `image_url` 内容块不报错，直接丢弃。
这就是「[缺失不能静默变成一个值](../问题定位/观测口径.md)」的又一个实例：
「没看到图」被读成了「图里没有东西」，然后模型用先验把空缺填满。

**判据**：不看回答质量（看不出来），看**会话日志里有没有 `read_image` 调用**。
`dsh_task.js` 已拒绝 `--images` 配非 `vision` 别名，并逐张核对读图路径。

**代价不对称**：放错一张图给非视觉别名就是一次幻觉，所以闸门按「带图 ⇒ 必须 `vision`」硬拦，而不是指望派工者记得。
现行别名表（纯文本默认 `flash`、带图 `vision`，底下同一个 V4.1-Flash）见 [DSH模型与视觉能力](DSH模型与视觉能力.md) 第一节；
09-08 时「默认模型定 `deepseek-v4-flash-vision-exp`」的旧做法已被那页的变更记录取代。

## ② headless 里图片靠 `read_image` 进去，不是附件

**为什么容易搞错**：DSH 的 Web UI 有附件功能（`dsh-attachment`），
适配器也支持 Files API 上传图片，看起来「喂图」应该是附件那条路。
**但 headless 的入口只有一个字符串任务**，没有附件通道 ——
图只能靠 agent 自己调 `read_image` 工具从磁盘读。

**推论**：「它有没有真看图」的判据**不是 token 数**（headless 侧看不到），
而是 `tool/call` 里 `read_image` 的**调用次数与参数路径**。

`dsh_task.js --images` 会自动在任务书前面追加逐张取图的强制指令，跑完逐张核对，缺一张判 FAIL。

## ③ 中文路径经 cmd.exe 会被打坏（仅 Windows；本机(Linux)/Linux 不受影响，但别退回 shell 调用）

**症状极具迷惑性**：DSH 回一句
「请您明确告诉我需要读取的是哪些图片，您可以直接提供图片的文件路径……」
看起来像它不听话、或者没权限、或者提示词写得不够清楚 ——
**实际是参数根本没送到它手里**。

**机制**：`dsh` 是个 `.cmd` shim。用 `spawn(..., {shell: true})` 调它会经过 `cmd.exe`，
Windows 默认代码页（本机 GBK）会把任务文本与路径里的非 ASCII 字符打坏。
本工程的路径几乎全是中文（`工程C/_渲染/_眼色三档对照.png`），必然踩中。

**实测**：2026-09-08，带中文路径的派工 **100% 读不到图**；
改成 `spawn(process.execPath, [bin.js, ...], {shell: false})` 后一次通过，9.5 秒答全对。

**判据**：看到 DSH 反问「要读哪些图片 / 找不到文件」时，
**先怀疑参数没送到，别急着改提示词**。验证方法：会话日志里看 `user/message` 的原文，
中文是不是乱的。

**已修**：`dsh_task.js` 直接调 `lib/bin.js`，不走 shim。
⚠ 自己手写调用时别退回 `dsh xxx` 那种写法。

## ④ 旧 API key 残留在**进程环境**里，压过凭据文件

**症状**：DSH 每次报 `QUOTA: Insufficient Balance`，而同一把新 key 直接 curl 全部通过 ——
含大 prompt（25K）、`max_tokens: 256000`、`reasoning_effort: high`、流式，**全组合都通**，
`/user/balance` 也显示有余额、`is_available: true`。

**真因**：适配器的凭据解析链是「`ctx.credentials` → 受信任的环境变量层」。
只要环境里有 `DEEPSEEK_API_KEY`，它就可能压过 `~/.dsh/.credentials.yaml` 里的正确 key。
本次环境里残留的是一把**已失效的旧 key**——教训：先确认进程里实际生效的是哪把 key（见下方判据），再谈余额。

⚠ **删 User / Machine 级环境变量，对已经在运行的进程无效** ——
它会一路继承到你从那个进程里起的每一个子进程。我当时确实删了两级，
但 `Process` 级那份还在，DSH 就一直在用失效的旧 key 干活。

**旁证**：按 key 分开看用量导出，新 key 上只有我直接 curl 的几次测试，
**派工的调用实际全记在旧 key 上**——新旧 key 混用时，按 key 查用量能直接定位是哪把在干活。
「新 key 怎么几乎没用量」这个现象本身就是线索。

**判据**（怀疑凭据问题时第一个查这个，别去查余额）：
```bash
node -e "console.log(process.env.DEEPSEEK_API_KEY)"   # 在**派工的那个 shell**里跑
```
输出非空、且尾号不是你以为的那把 → 就是它。

**已修**：`dsh_task.js` 在 spawn 子进程前把 `DEEPSEEK_API_KEY` 从 env 里删掉，
强制走凭据文件。**自己手写 dsh 调用时也要这么做。**

**更一般的教训**：换密钥时「设置新的」只是一半，**另一半是确认旧的在每一层都消失了** ——
文件、User 级、Machine 级、以及**已在运行的进程**。少一层就会得到一个
「配置看着全对、行为却不对」的局面，而且报错信息（余额不足）指向的是完全错误的方向。

> 以下两节 2026-09-18 从 [DSH派工](DSH派工.md) 下沉。

## ⑤ `read_image` **被拒**也算「读了」（2026-09-10 补）

`--images` 的核验原来只数会话日志里 `read_image` 的 **tool/call 条数**，不看结果。
v4.1 预览到期那天三次调用全被拒，call 照样有三条 ⇒ 核验打印 **「读图 3/3」并判 ✓ PASS**，
而模型一张图都没看见。（它自己在回答里老老实实写了「我没能看到这三张图」，
否则这份回答会被当成正常评审采信。）

另有一条连带教训：**同一个模型的第一次派工 900 秒超时、零产出**，当时误判成「它不守规矩，
跑去写像素分析脚本」——复盘会话日志才发现，那三次 `read_image` 同样是被拒的，
它是在**用 python 补一个自己没有的能力**。⇒ 超时先看工具结果，别先怪模型发散。

⇒ `dsh_task.js` 已改成按 `callId` 回查 `tool/result` 的 `isError`，
被拒的不计入「读图 N/M」并直接判 FAIL。回归验过：vision-exp 那次 3/3 通过、
`expires-on-0910` 两次都 FAIL。
⚠ 09-11 更正：那两次 FAIL 是**别名没声明图像输入**，不是模型没有视觉能力，
  详见 [DSH模型与视觉能力](DSH模型与视觉能力.md) 页末变更记录。这道闸门本身仍然要留 —— 它拦的是形态，不是某个模型。
**教训：模型能力会过期，文档里的历史结论不能当准入依据 —— 加白名单前先真跑一次。**

## ⑥ `--brief` + 并发 ⇒ 核验张冠李戴（2026-09-11 修）

认领会话的指纹原来取 `task.slice(0, 120)`。而 **`--brief` 会给每一路任务前置同一段
固定抬头**（「先读这个 —— 本工程的事实速查档」…），那段远超 120 字
⇒ **所有路的指纹完全相同**。并发派 5 路时五个进程都认领了同一个会话，
核验块报出的模型 / 工具 / 收尾全是别人的。

**实测症状**：三路报同一个 `session id`、都判 `✗ FAIL`（收尾 `?`），
**而三份回答其实都是好的、各自对题** —— 典型的「核验比任务先坏」。
危险在于它的方向：**把好结果误判成坏的**，容易让人白白重跑一遍（花两倍的钱）。

⇒ 已改成在任务末尾埋一次性 nonce（`dsh-task-<pid>-<base36 时间>`），按它认领。
   ⚠ nonce 必须在 spawn **之前**拼进 task，否则子进程根本没见过它。
   回归验过：两路并发 + 共用同一 `--brief` 抬头，各自认领到不同 session，双双 PASS。

**顺带一条判读规则**：核验判 FAIL 时，先看 FAIL 的**理由**。
「收尾不是 completed」+ stdout 却有完整答案 ⇒ 多半是认领错了会话，不是任务失败。
真正该重跑的是 stdout 为空、或答非所问的那种。
