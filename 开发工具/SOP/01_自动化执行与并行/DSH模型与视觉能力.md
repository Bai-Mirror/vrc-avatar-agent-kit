# DSH 的模型、价格与视觉能力边界

这页解决的问题：**派工选哪个模型、带图能不能派、花多少钱**。

## 一、模型别名（现行；以 `通用工具/dsh_task.js` 的 `MODELS` 表为准）

2026-09-11 起 DeepSeek 只剩**一个**模型：**DeepSeek-V4.1-Flash**（支持图像理解、1M 上下文、最大输出 384K、并发 2500）。
下表三个别名底下都是它，都按 Flash 价计费；差别只在 **DSH 这个 harness 给哪个名字声明了图像输入**。

| `--model` 别名 | 实际 model id | 什么时候用 |
|---|---|---|
| **`flash`（默认）** | `deepseek-flash` | **纯文本任务** |
| **`vision`** | `deepseek-v4-flash-vision-exp` | **带图任务必须用它**；`--images` 只放行这个别名（`VISION_CAPABLE`） |
| `v41` | `deepseek-flash` | 只为兼容旧命令行 |
| ⛔ ~~`pro`~~ | ~~`deepseek-v4-pro`~~ | **禁用，见下** |

**为什么带图不能用 `flash`**：`deepseek-flash` 传图会被硬拒
`model "deepseek-flash" does not declare image input` —— 不是模型不行（官方《模型细节》写着图像理解=支持），
是 harness 的能力声明里没给这个名字加图像输入。`deepseek-v4-flash-vision-exp` 这个**名字**是旧模型下线后留下的别名，
原模型已不在，请求由 V4.1-Flash 承接，但它在 harness 里声明了图像输入 —— 保留它**只为这一条声明**。
**教训**：「同一个模型」不等于「同一套能力声明」，能力要按**别名**实测，不能按模型推；也别拿过期别名的行为推断模型（见页末变更记录）。

⇒ **纯文本 `--model flash`（缺省即是）；带图一律 `--model vision`。** 其余旧名（`deepseek-v4-flash` 等）虽然仍可调用，别再写。
北京工作日高峰 `--engine auto` 会改派 Codex，flash/vision 的任务书落到 `luna` 档 → [Codex派工](Codex派工.md)。

**这条是闸门救场抓出来的**（09-11）：三路设计评审里有两路在**没看到图**的情况下写了 18KB 的方案，
若没有那道「回查 `tool/result` 的 isError」的闸门，会被当成正常结论并进汇总（→ [DSH静默失败](DSH静默失败.md) ⑤）。

### ⛔⛔ Pro 是硬禁，只有作者能解禁

**作者 2026-09-11 明令：「现在绝对不允许使用 Pro，除非以后我再解禁。」**
这不是「一般不用」的偏好，是**红线**。「这个任务好像更适合 pro」不构成理由。

拦截做了四层（都实测过）：
1. `dsh_task.js` 的 `BANNED` 别名表 —— `--model pro` 直接退出；
2. `BANNED_ID` 正则 —— 连 `--model deepseek-v4-pro`、`DEEPSEEK-V4-PRO` 这种绕过别名的写法也挡；
3. **事后核验** —— 会话日志里真实模型命中 Pro 一律判 FAIL。
   这一层不能省：DSH 的 **web UI 切模型会把 `agent-default-model` 写回
   `~/.dsh/settings.yaml`**，而那一层优先级高于本脚本的 `--patch`，
   「派工时挡住」≠「实际没跑 pro」。
4. `~/.dsh/settings.yaml` 的 `allowedModels` 现在只剩 `deepseek-flash`。

附带事实（不是禁用理由，理由是作者的决定）：Pro 不支持图像理解、并发只有 500、
价格贵 4.5 倍，且 09-14 12:00 后请求也会被路由到 V4.1-Flash。

## 二、视觉能力边界（2026-09-08 实测，合成图带 ground truth + 真实渲图）

⚠ 下表是 2026-09-08 在**旧模型** `deepseek-v4-flash-vision-exp` 上测的。
该模型 09-11 起已下线，请求由 `deepseek-flash`(V4.1-Flash) 承接 —— **下面这些能力边界还没在新模型上复测过**，当参考、别当结论。
当年那版：**视觉输入被恒定压到 315–396 token**——
1.5MP 的渲图和 5KB 的合成图花的 token 一样多，所以精度上限是结构性的，**喂大图不解决**。

| 能力 | 实测 | 能不能派 |
|---|---|---|
| 小字 OCR（10px 起）、中文标注、印在图上的 hex | 全对 | ✅ 可靠 |
| 结构语义（几个面板、哪个标了默认） | 全对 | ✅ 可靠 |
| 相对大小比较（差 5.8%） | 对 | ✅ 可靠 |
| 色彩排序（谁更饱和） | 对 | ✅ 可靠 |
| 局部缝隙有无 | 1px 判无、2px 判有（2/2 稳定） | ⚠ 阈值 ≈ 0.14% 画幅 |
| 精确取色 | 单通道最大偏 10/255（4%） | ❌ 只能定色系 |
| 精确计数 | 23 → 24 | ❌ |
| 跨区域对齐 | 6px（0.86% 画幅）判成「完全对齐」，2/2 复现 | ❌ **确定性失败** |

**为什么能看见 0.14% 的缝、却看不见 6 倍大的错位**：缝是局部高对比特征，
对齐要跨区域空间配准 —— 视觉预算不够做后者。所以判据要按这条分，不按「差多大」分。

**两条能直接用的规则**

1. **「有没有 / 是不是 / 哪个更X」→ 让它看图。「差多少 / 有几个 / 齐不齐」→ 走几何量。**

   「走几何量」的具体入口（不是让它看图，是让它**取数**）：
   - Blender：`mcp__Blender__execute_blender_code` 跑 `bpy` 读顶点/骨骼/包围盒 →
     顶点位移与形态键量法见 [30/五官缩放几何](../30_捏脸/五官缩放几何.md)
   - Unity：`mcp__UnityMCP__manage_gameobject` / `find_gameobjects` 读 transform、
     `mcp__UnityMCP__unity_reflect` 读组件字段；环状件位姿解法见 [55/环状件位姿求解](../55_配饰装位/环状件位姿求解.md)
   - 纯文件层：`pwsh` / `read` 直接解析 `.anim`、`.prefab`、`.mat` 文本 —— 判据要贴着权威产物

2. **把数值印进图里让它读，别让它测。** 它读印在图上的 hex 字符 100% 准，
   自己感知颜色却偏 4%。**手段**：渲图后用 Python + PIL 叠字
   （`ImageDraw.text`，参照 `通用工具/` 里现成的对照图生成脚本），把该判的数
   （hex、mm、编号、档位名）直接画在对应面板下方 —— 这就是 `_眼色三档对照.png` 的做法，
   实测三个 hex 它一次读全对。判据于是从「不可靠」变「可靠」。

## 三、价格（官方《模型细节》，元/百万 token）

| | 缓存命中输入 | 缓存未命中输入 | 输出 |
|---|---|---|---|
| flash · **空闲** | 0.02 | 1 | 4 |
| flash · 高峰 | 0.04 | 2 | 8 |
| pro · 空闲 | 0.15 | 4.5 | 13.5 |
| pro · 高峰 | 0.30 | 9.0 | 27.0 |

**高峰 = 北京时间 周一~周五 09:00-12:00、14:00-18:00；其余空闲，价格减半。**
⇒ 大批量派工尽量排在空闲时段，直接省一半。

**用量与费用统计**：`node 开发工具/通用工具/dsh_usage.js [--since <ISO>] [--dir <过滤>] [--json]`
它从会话日志里 `assistant/chunk` 的 `usage` 事件取数（同一 step 只取最后一条累计值），
按上表分时段计价。**已用真值校准过**：按会话日志估算的费用与后台账单能对上，可作估算依据。

**缓存有多值钱**：缓存命中能把实付压到远低于「全部按未命中计价」的水平——
**估算费用与选型时要把缓存命中算进去**，别按全未命中估。
所以**别怕上下文长，怕的是重复摄入**（这正是 `--brief` 存在的理由）。
