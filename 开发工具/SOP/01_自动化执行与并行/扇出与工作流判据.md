# 扇出单位、工作流判据、就绪度评级

这页解决的问题：**一件事重复 N 遍时，值不值得开多代理并行算**，以及每个阶段离全自动还差什么。
排期与依赖看主页，这里是决定「开不开工作流」的三张表。

---

## 一、阶段内可扇出的单位

「扇出」＝ 同一件事重复 N 遍且彼此独立，适合多代理并行**算清单**。

| 阶段 | 扇出单位 | 独立性 | 备注 |
|---|---|---|---|
| 20 素材导入 | 每个素材包的**清点与完整性判定** | 独立 | ⚠ **导入动作本身必须串行**：同商品的几个分包会共用文件夹/材质 GUID，并发导入会互相吞资产 |
| 40 贴图配色 | 每个配色候选的生成与打分 | 独立 | 施加到工程仍要串行 |
| 55 配饰装位 | 每件配饰的位姿计算 | 独立 | 位姿全算出来写成表，再一次性落场景 |
| 70 回归测试 | 每个组合的**判定** | 独立 | 用真动画数据 `Apply` 参数即可，不需要烘焙 |
| 80 性能优化 | 每张贴图的分级判定、每条动骨链的挂载判据 | 独立 | 判据是闭式的，天然适合扇出 |
| 05 评审 | 每个模型 | 独立 | 本来就是并行编成 |

**不能扇出的**：任何需要烘焙的（贵且互斥）、素材导入动作、场景写入。

---

## 二、什么时候值得开多代理工作流

**值得**（同时满足才开）：

1. 单位数量 ≥ 5
2. 每个单位是**只读 + 计算**，产出是一行结论或一段清单
3. 判据是闭式的（数字、布尔、枚举），不依赖跨单位的上下文

典型：配饰装位的位姿计算、贴图分级、组合回归的判定、跨模型评审、大批量文档改写。

**不值得**：

- 要动 Unity 的（并行没有意义，反而会互相打断）
- 单位数 < 5（编排开销大于收益）
- 判据要看图（图的粒度、机位都要统一，扇出反而增加不一致）
- 有顺序依赖的（素材导入、层序设计）

## 三、自动化就绪度评级

| 阶段 | 评级 | 卡在哪 |
|---|---|---|
| 10 接单建档 | **全自动** | — |
| 20 素材清点导入 | **全自动** | 导入动作串行即可 |
| 30a 捏脸调值 | 人工 | 审美 |
| 30b 烘焙导出校验 | **全自动** | — |
| 35 面部追踪 | **全自动** | ⚠ 安装器会克隆头像，按名字找头像的工具会改错对象 |
| 40 贴图配色 | 半自动 | 定案要人点头；出候选与评审全自动 |
| 50 服装发型装配 | **全自动** | — |
| 55 配饰装位 | **全自动** | 位姿有闭式判据；观感问题走评审 |
| 60 菜单与动画层 | **全自动** | 层序设计要按既定惯例，不要现场发挥 |
| 70 回归测试 | 半自动 | 平台覆盖类改动**编辑器验不出来**，必须真机 |
| 80 性能优化 | **全自动** | 动骨观感改动只能在 Play 里看 |
| 90 交付打包 | **全自动** | — |
| 95 上传终审 | 人工 | SDK 上传必须人操作 |

**净结论**：14 段里 9 段可以全自动，3 段半自动，真正的人工只有 2 段。
瓶颈不在自动化能力，在**卡口的排队**。

## 四、第二阶段的扇出量 = 第一阶段的**产出条数** × 视角数，必须自己封顶

**触发时刻**：写 `pipeline(items, 查, 逐条验)` 这种两段式工作流时。

**踩过（2026-09-20，poke 假阴性排查）**：第一段 4 个排查 Agent，我以为扇出就是 4。
实际第二段是「**每条发现** × 2 个反驳视角」，而 4 个 Agent 各交了 8–11 条发现 → 4 × 9 × 2 ≈ **70 个子 Agent**。
用户看到 70 个并发才发现不对，我自己没察觉。

**可查问句**（发起前必问）：
> 我限制的是**维度数**还是**第二阶段的总数**？第一阶段每个 Agent 会交几条？条数是**模型定的**还是我定的？

**规矩**：凡是下一阶段的规模由上一阶段的**输出条数**决定，就必须在脚本里显式封顶：

```js
const TOP = 3                                   // 每个维度最多验几条
const picked = (res.findings || [])
  .filter(f => f.confidence !== 'low')          // 先按置信度筛
  .slice(0, TOP)                                // 再硬切
```

**取舍**：封顶会漏掉排在后面的发现。代价可接受，因为
① 让第一阶段按重要性排序输出；② 真漏了可以带着已有结论再跑一轮定向的。
反过来不封顶的代价是**不可控**——条数是模型自由发挥的，可能 3 条也可能 30 条。

**另一条**：schema 里给数组加 `maxItems` 只能约束单个 Agent 的输出，
约束不了「维度数 × 每维条数」的乘积，别拿它当封顶。
