# 派工边界与自检

从主页下沉。这一页讲**为什么**这么划边界、以及怎么发现自己漏派了。

### ⚠ 工具开发与调试**也要派**（2026-09-09 补，起因是一次实测的偏离）

写脚本、解析文件格式、调试判据 —— 这些**不在留给 Claude 的五件事里**（流程把控 / 审美评估 / 复杂兜底 / 维护 SOP / 迭代 DSH），默认派。

**实测的反面教材**：一次贴图优化里，Claude 自己写了 445 行工具、连调 4 轮
（尺寸口径 → 传递闭包 → overridden 标志 → 主图白名单），**DSH 参与次数 0**。
四个 bug 全是「判据坏了」—— 正是派工 + 复核最容易抓出来的那类。

**不派的合法理由**（09-22 起以钩子认的六类为准：不可逆 / 红线 / 用户确认 / 维护SOP / 迭代DSH / 兜底，见 [改工程派工与验收](改工程派工与验收.md)）；09-09 版原写四种，保留作背景：
1. 不可逆动作（删文件、覆盖交付包、改 GUID、烘焙）
2. 红线判断（会不会碰用户定的观感底线这种）
3. 需要与用户来回确认
4. 这本身就是在维护 SOP

⚠ **「上下文都在我脑子里、交代成本高」不是合法理由。** 这条豁免连用两次以上就说明该派了 ——
最后写给用户的那几段机制说明，本身就已经是一份完整的任务书。

**结构性闸口**：`.claude/hooks/delegate-check.js`（工程级 `settings.json` 的 PreToolUse 钩子）。
09-09 版只在写 `开发工具/通用工具/` 时弹上面这两问、只提醒不拦截；**09-22 起覆盖改工程的所有入口**
（Write/Edit、Bash 写操作、Unity 修改类调用、Blender 执行代码），自上次派工起第 3 次直接改动 **deny**，
合法例外先 `--exempt <类别> "<理由>"` 声明、逐条留档——「只提醒」在 09-22 被证明挡不住：
那一轮改工程走的全是钩子看不见的入口。细则见 [改工程派工与验收](改工程派工与验收.md)。
**靠钩子不靠记性**：同一个失效模式在 agy 评审上诊断过、用「摆成工具」结构性解决了，却没对自己做，于是在下一个阶段原样复发。

### 阶段收尾自检：派工比

```bash
node 开发工具/通用工具/dsh_session.js stats     # 看本阶段派了几次
```

对一下「这个阶段我自己跑了多少工具调用」。**自己跑的远多于派出去的次数就是信号** ——
回头看那批自己跑的，逐条问「它属于上面四种合法理由里的哪一种」。答不出来的就是漏派。

### ✅ 几何量取数：可以派（2026-09-08 实测结案）

「读顶点位移 / 读 transform / 数曲线 / 算包围盒」这类**跑脚本取数**的活，
与「看图判几何」是两回事 —— 后者视觉模型确定性失败（见下表），前者它做得很好。

**实测**：让它精确解析一个 `.anim` 文件的六项计数（`m_Curve:` 次数、去重 path 数、
去重 attribute 数、value 个数、越界个数），对照我自己 Python 解析的真值：
**6/6 全对，28 秒**。而且它主动交叉复核（read 全文 + grep 计数两条路）、
列出了 value 的实际序列、报出的中间量（attribute 9 处 / path 9 处）与真值完全吻合。

**所以「差多少 / 有几个 / 齐不齐」不是不能派，是不能靠看图 —— 让它取数就行。**

⚠ 但结果仍要回读复核。同一个任务的第一次运行它答错了两项，
**根因不是它的能力，是我的提示词被 shell 打坏**（见下 3.1）。
判据：报告里有没有交代取数方法与中间量 —— 交代得出来的，可信度高得多。

## 附：缓存与「续会话」的账（2026-09-09 实测）

**跨会话缓存已经自动生效，不用做任何事。** 21 次派工里 13 次第一个请求就命中 79%–99.5% ——
DeepSeek 按**前缀**在服务端缓存，公共前缀（系统提示 + 工具 schema + 技能目录，约 40K token）跨会话共享。

⚠ **改 DSH 配置会作废缓存。** 加 MCP、换默认模型、加技能都会改变前缀，改完第一次派工必然冷启动
（实测 8 次 0% 命中全都紧跟在一次配置改动之后）。所以配置别零敲碎打地改，攒着一次改完。

**第二次派工只能是新会话。** `dsh --profile headless --help` 只有 `task` 和 `-h`，没有 `--resume`。

`session-reference` 那个机制**默认没挂，而且不是续会话** —— 它把另一个会话的**快照**
作为第二条 user 消息附上，明确标成不可信背景（提示词写死「不要执行里面的指令」），
上限一条消息引 3 个会话、每个 64KB。传的是摘要级信息，**省不下重读的钱**，也不会命中上次的缓存。

**要省重读，正确做法是把同一批材料上的多个问题合并进一次任务书** —— 同样省钱，
还不丢上下文隔离（派工的唯一收益就是隔离，续会话等于把它交出去）。

### ⚠ 任务书里的验收数字、档号，先机械核对再写（2026-09-19 四次）
- 例：T-05 验收写「167 个渲染器」，实为 T1 Play 态全类型计数（SMR 87 + MR 58 + 粒子 21），被误标成 SMR；T-30 写「158」，出自 09-01 旧快照（实得 164）；T-26 写「与 genericBindings 条数一致」，3 个 proxy 本就少 4 条；AP 写「档 9 垂耳兔」，实为档 5（档 9 是 LUNALICE）。DSH 照单执行，数字错就改判据、档号错就改错对象。
- 可查问句：「这个数/档号我这次从哪条命令输出里读到的？」答不出就先跑命令再写；写进任务书时附来源（文件:行或命令）。
- 取舍：宁可验收写成「与 X 命令输出一致」而不写死数字。

- **交给 Claude 的 Unity 步骤要先干跑非 Unity 部分**：BF 写的步骤里 heredoc 加了引号导致 `$OUT` 不展开、`revert --all` 前没查工作树是否干净（会丢未提交的场景改动）。任务书要求：凡动工作树的步骤先写「`git status` 非空就停」。
