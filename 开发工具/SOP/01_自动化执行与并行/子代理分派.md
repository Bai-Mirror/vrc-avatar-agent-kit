# 子代理分派：派谁、派不派、怎么验

### 派哪一档模型：按「有没有工具看不见的推理」分，不按模型强弱

| 任务性质 | 判据 | 派谁 |
|---|---|---|
| **枚举型** —— 产出是清单/计数，每一行都能被某次工具调用**直接印证** | 列目录、数文件、抽字段、跑现成脚本 | **Haiku**，便宜一个数量级 |
| **推理型** —— 要跨文件比对、判等价/兼容/根因 | 需要「综合几处证据」 | **Sonnet** |
| **审美型** —— 没有闭式判据，要的是取舍和落点 | 捏脸方向、配色、风格收敛 | **Fable** |
| **排障** —— 别路卡住、判据自相矛盾、要推翻前面某路的结论 | 多层套一层的根因 | **Opus**，见下 |

#### 什么时候派 **Opus 子代理**，什么时候自己做

派子代理的**唯一收益是上下文隔离**：付一份任务描述 + 一份回报，中间过程不进主代理上下文。
所以 Opus 子代理值不值，看三个条件是否**同时**成立：

1. **确实需要 Opus 级判断** —— Sonnet 会在这里停下或走偏
2. **中间证据量大且噪声高，但结论可压缩成几行** —— 大段日志、扫上百个包、二进制解析
3. **动作可逆或纯只读**

判据是「**答错的代价 > 派它的成本**」，不是「这题有点难」。Opus 子代理很贵。

**2026-09-06 的两个正例**（当时是主代理自己做的，其实该派）：

| 案例 | 形状 |
|---|---|
| BlendShare 编译链 | 三层套一层：缺分号 → 补了还剩 72 个 FBX 类型找不到 → 根因是 **UPM 不读 `Assets/` 下的 package.json**。中间翻了 asmdef、包缓存、上一单的 `packages-lock`、日志尾巴，全是噪声，结论三行 |
| 某厂商材质的 GUID 取证 | 扫 134 个 zip、比对 `.meta` 时间戳、追厂商版本历史，结论是**一个 GUID 值** |

那一轮 Sonnet（断引用定性那路）**正确地停在了第一层**并触发 STOP ——
它没做错，是那个判断超出了它该做的范围。**STOP 写对了，弱模型就不会硬撑。**

**不派、自己做**的四种：

- **不可逆动作** —— GUID 修复、烘焙、打包、删文件（用户定的「高风险我来」）
- **中间证据后面还要用** —— 比如 90 条形态键的索引表，主代理得留着
- **任务很短** —— 描述成本大于收益
- **需要跟用户来回确认** —— 子代理问不了人

**还有一类值得试（本单未用）**：拿 Opus 子代理去**独立复核另一路的结论** ——
它上下文干净、不会被前一路的措辞锚定，相当于一个对抗性验证者。

#### 派 Haiku 必须在任务描述里**写死禁止做哪类判断**

实测（2026-09-06 素材清点）：它报「两个 zip 内容完全相同」，实际差 376,062 字节。
**它没打开过 zip，也不可能打开** —— 是任务描述让它去判「等价」。
它列文件名与字节大小那部分是准的。**失败的是描述，不是模型。**

正确写法：「**只报文件名与字节大小，不要判断内容是否等价**」。

#### 怎么知道该禁哪些判断（不要靠经验，逐条推）

对任务里要它给的**每一条结论**，问：

> **「这条结论要成立，它必须**做过**什么动作？」**

把那个动作写出来；**如果动作不在它的工具能力范围内，就把这条结论禁掉**，
并换成一个它做得到的替代物。

| 结论 | 必须做过的动作 | Haiku 做得到吗 | 处置 |
|---|---|---|---|
| 「两个 zip 内容相同」 | 解开并逐条目比对 | ✗（只会列目录） | **禁掉**，换成「只报文件名与字节大小」 |
| 「这两个包功能等价」 | 读 README / 装进工程试 | ✗ | 禁掉，换成「列出两个包各自的顶层目录」 |
| 「这批文件都在」 | 遍历并比对清单 | ✓ | 保留 |

**判错的代价不对称**：
- **禁多了** → 它把本来能做的判断也交回来，你多做一轮（**代价小**）
- **禁少了** → 它编一个结论，而执行型报告你**容易直接采信**（**代价大得多**）

**所以宁可禁多。**

#### 验收规矩：结论要跟工具调用对得上

> **子代理报告里凡是「我没做那个动作就得不出的结论」，一律不采信，自己复核。**
>
> 列目录得不出「zip 内容相同」，读文件名得不出「功能等价」，
> 截断的日志尾巴得不出病因，看一眼截图得不出「骨骼没错位」。

这跟 [05 多模型评审](../05_多模型评审规程.md) 里「它指的**位置**比它给的**结论**可信」
是同一个规律，而且**执行型子代理更危险** ——
评审结论我天然会复核，执行报告我容易直接采信。

**有效的做法**：把**前几次编造的具体实例**写进任务描述的「报告纪律」段。
实测比抽象地写「不要编造」有效得多 —— 加了之后，后续几路都主动在没把握的条目上标了「未验证」。

#### 子代理**不会等后台任务**（3/3 复现）

起了 batchmode / 后台脚本就交回合，它没有轮询能力。**这不是偷懒，是回合语义。**

- 任务描述里要写死「**起完必须轮询等它退出再读结果，不要中途回报**」
- **主代理必须自己复核终态**，不能采信「还在跑」
- **子代理中断 ≠ 工作丢失** —— 先去看磁盘上有什么，再决定重派还是接着推

## 搜索类任务：**范围由你列全，别让子代理自己划边界**

**触发时刻**：派「找 X 素材／找 X 文件」这类穷尽搜索。

**踩过（2026-09-20，找 Milfy 眼贴图）**：我写的任务书第一句是「在工作区 `~/vrc-processing` 里搜」，
子代理照办，交回一份工作区内的穷尽清单——**清单本身没问题，边界是错的**。
用户一句「在更广泛的素材区中去寻找」才暴露：本机有**三个**素材区，
而且**检索顺序早就记在记忆里**（`<素材库>` 主库 → 客户素材包 → 百度后备库），是我派活时没照着列。

**可查问句**（写任务书时问自己）：

> 这类东西在本机一共有几个存放点？我是**列全了**，还是只写了我最熟的那个？

**做法**：
1. 先自己花一两条命令把**存放点列全**（`df -h` 看挂载、翻记忆里的「资源位置」条目、读库自带的 `_库说明`），
   再写任务书；任务书里**逐条写死路径**，不要写「在工作区里找」这种由子代理去理解的范围。
2. 每个存放点标注**是否只读**（存档库、客户素材包都是只读的，要在任务书里明确禁止写入）。
3. 存放点自带索引/元数据的（如 `<素材库>/.booth-archive/manifest.json` 有 `avatars` 字段），
   **先自己查索引再派人**——能筛掉的就别让子代理去拆包。这次靠 manifest 一条命令就筛出了 3 个支持 Milfy 的眼贴图包。

**取舍**：列全边界要多花几分钟；不列的代价是整轮返工，而且**返工前你还以为自己"穷尽"过了**——
这比单纯漏掉更糟，因为它会让你对结论过度自信。
