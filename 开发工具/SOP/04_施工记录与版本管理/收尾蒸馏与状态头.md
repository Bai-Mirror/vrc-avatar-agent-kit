# 收尾蒸馏与状态头（两层制，作者 2026-09-23 拍板）

## 为什么改成两层
09-23 工作流审理（`_工作流审理_20260923.md`）查实：执行会话在疲劳上下文里随做随记 SOP，结果是跨页矛盾（「四件事 / 五件 / 六类」）、只拆不缩（27 个子页按行搬运）、DSH 技能文件与 `--record` 相反；而 `排障记录规程` 又证明「事后补记会被合理化」。两边都对，所以拆层：**现象层当场记，规则层收尾蒸馏。**

## 现象层（执行会话，随做随记）
- 只写事实：动作、触发的异常输出、当时的假设、证伪/证实的证据。落点是该工程 `_施工记录.md`（`log_step.py`）或 DSH 回复的「应写进 SOP 的教训」段（进流水账）。
- 撞墙或被纠正时加 `--distill "触发时刻＋可查问句"`，条目里出现「待蒸馏」标签即可，**不改 SOP 主体**。
- 例外：不改就会让**下一次派工立刻踩坑**的判据（例：某工具名、某参数值错了）允许当场改 SOP 一行，并在标签里写「已当场写入 X 页」，蒸馏时复核。

## 规则层（收尾，干净上下文）
**什么时候**：一个阶段收尾、或一天结束、或 `baseline_recheck.sh` 报「待蒸馏标签 ≥ 8 条」时。
**谁**：一个不带对话历史的代理——Claude 子代理（`Agent` 工具，只给材料包与点名页）或一次 DSH 派工（`--no-record`）。不能是正在干活的那个会话。
**输入**：`python3 开发工具/通用工具/distill_collect.py --since "$(上次蒸馏时间)" --out 材料包.md`（三节：待蒸馏标签、DSH 教训段、这段时间被改过的 SOP 页）。
**动作**（材料包末尾也印着）：
1. 每条标签/教训先 `grep` SOP 有没有同义条目；有就在原处改（补触发时刻、可查问句、取舍），没有才加，加在最贴的页。
2. 被改过的页逐页：字节数（>10,240 拆子页，步骤表与判据留主页）、`python3 开发工具/通用工具/check_links.py [--baseline <改前快照>/开发工具/SOP]` 死链、同主题跨页矛盾（数字、件数、类别）。拆页前**现拍**快照（按 `bh_prep.py` 口径另存本轮 `before_<轮>/`，别复用跨轮 `tmp/bh/before/`：09-19 存档到 W2 已过期，`check_lines.py` 误报旧行缺失）；超限判据只数**本轮责任页**，并行任务正在写的页（W2 时 [00_总表/工具索引](../00_总表/工具索引.md) 26 KB）在回报里标来路、不计。
3. 不改施工记录、不改流水账；产出一份「已并入 → 页:节」清单。
4. `distill_collect.py --mark "<一句话>"` 记时间，`ws_git.py commit` 只点名改过的 SOP 页。
**验收（Claude）**：抽 3 条标签在 SOP 里 grep 得到；`find SOP -size +10240c` 只剩豁免页（并行任务在写的页须标明来路）；`python3 开发工具/通用工具/check_links.py` 新增断链为 0（改前已断的用 `--baseline` 豁免）。

**取舍**：蒸馏晚于事故几小时到一天，代价是这期间的派工读不到新规则——所以留了「立刻踩坑」例外。反过来若不拆层，代价是 09-18 至 09-23 那种每天 20 多次 SOP 提交、页页贴着 10 KB、四处矛盾。

## 状态头
每个工程 `_施工记录.md` 顶部、`>` 说明段之后：
```
<!-- 状态头:BEGIN（可整块改写，由 log_step.py 或验收者维护；下面的时间线只追加不改） -->
## 当前状态（YYYY-MM-DD HH:MM）
- **阶段 / 交付状态**：80 性能优化 / 进行中
- **最近一步**：<最后一条标题>
- **下一步**：  1. …（来源 路径:行）
- **未决 / 等用户**：  - …
- **不许动**：<用户禁区>
<!-- 状态头:END -->
```
接手：`log_step.py <工程> --show`。每次 `log_step.py` 追加条目时可顺手 `--stage/--next/--pending/--forbid` 改状态头；不给就只更新「最近一步」。`baseline_recheck.sh` 会把七个工程的状态头摘要一起打出来。

## 事故记录：时间戳（为什么时间只能来自时钟）
- **条目时间用 `date` 取，不凭感觉写**（2026-09-18 两次写出比实际晚 10–20 分钟的时间戳）：长任务里对时间的感知会漂，写条目前先跑一次 `date +%H:%M`。09-19 又犯且更严重：一个下午连写 6 条比实际**晚 25–105 分钟**的「未来时间」（上下文压缩后按任务量估时间）。自查：新条目时间不得晚于 `date`，也不该早于上一次提交（`git log -1 --format=%ad --date=format:%H:%M`）。
  - **09-20 又犯两次**（17:05 写成 17:05 实际 16:33、17:14 实际 17:10）：两次都是**先把整条记录写好、`date` 放在同一条命令里一起跑**，结果时间是"我以为的"而不是 `date` 的。**改法**：`date` 的输出要**先看到**，再把那个数字抄进条目；别把 `date` 和 `cat >> 施工记录` 放进同一条命令。自查：这条时间戳，我是从哪个工具输出里抄的？
  - **09-22 夜间第三次复犯**：用户休息时连续推进 2 小时，20 条条目写成比实际晚 15–60 分钟的「未来时间」（05:1x–07:2x，实际 04:53–06:33），直到一次把 `date` 与写条目放同一条命令时才看到 06:33。按 `git log --date=format:%H:%M` 逐条改正。同日第四次：`AskUserQuestion` 等了约 4 小时才有回答，我按提问前的时间把拍板记成 14:4x（实际约 18:00）。**`AskUserQuestion` 返回后先跑 `date` 再记拍板时间**——用户可能隔几小时才答。**改法补一条**：每次验收前先单独跑一次 `date +%H:%M`，条目里只写这个数，不写「0x」式估时。
