# 60 · 人形手臂与手指

> ← [60 · 菜单与动画层](../60_菜单与动画层.md)

这页解决的问题：需要一段涉及手臂/手指的人形姿势（抱物、持物），且关掉时移动、手势、呼吸都要完全正常 ——
该占哪个可播放层、遮罩为什么做不到「按需接管」、手指怎么用权重驱动，以及桌面与 VR 各自不出姿势的原因。

## 让人形手臂动起来：三条路线，代价各不相同

需求长这样：「抱住怀里的东西」「拿着道具」—— 要一段**涉及手臂**的人形姿势，
而且**关掉的时候一切要正常**。这件事在 VRChat 里没有免费方案，先把约束摆清楚。

### 硬约束：可播放层遮罩是构建期固定的

| # | 在哪 | 说明 |
|---|---|---|
| ① | **可播放层遮罩** | 构建期从「合并后控制器**层 0** 的 `avatarMask`」取。改描述器上的 `mask` 字段没用 —— NDMF 与 VRCFury 都会覆盖它 |
| ② | 控制器内部每个 layer 自己的 `avatarMask` | 只管这一层写什么 |

②被①包着：**①没开的部位，②再怎么开也写不出去。**
而①**不能在运行时切换**，所以「只在需要时占有手臂」这个诉求，用遮罩做不到。

**把自造空层顶到 layer 0 的手法**：加第二个 MA MergeAnimator + `layerPriority` 取负数（NDMF 里越小越靠前）；实测厂商原 layer 0 移位后 `defaultWeight` 仍为 1。

### ⚠ 遮罩开了某个部位，就必须一直有人写它

这是最容易踩的一条。人形层的行为不是「没写就穿透下层」，而是：

> **遮罩认领了某个部位、却没有任何曲线写它 → 输出人形零姿势（肌肉全 0）。**

后果两条，都很难自查：

- **手臂**：零姿势是直臂贴身，比站姿更难看。所以一旦把手臂放进遮罩，
  就必须每帧写一个姿势 —— 于是**移动层的摆臂永远出不来**。
- **手指**：零姿势是**微微成爪**。如果那一层的遮罩含手指、clip 里却没有手指曲线，
  它会把下面厂商的手势层整个盖掉 —— 症状是「手势表情全失效，手一直半握」。

**推论**：手臂层和手指层**必须拆开**，各用各的遮罩。
一层同时管两者，就没法做到「手臂常驻、手指按需」。

### 三条路线

| 路线 | 关掉时 | 打开时 | 代价 |
|---|---|---|---|
| **甲 Gesture 占手臂** | 手臂被写死成某个姿势 | 姿势精确 | 移动/坐姿/第三方姿势插件下手臂全错 |
| **乙 手臂还给移动层** | **完全正常** | 手臂不参与，物件只能挂着 | 放弃手臂姿势 |
| **丙 Additive 叠加层** | **完全正常**（零增量） | 站立时精确，移动时是「摆臂＋偏移」 | 见下面的坑 |

**丙通常是最优解**，因为 Additive 层的性质正好对口：

> 叠加层「没写」＝「加 0」＝**真的没有影响**；
> 而 Override 层「没写」＝掉人形零姿势。

选丙之前先确认 **Additive 可播放层没被占用**（描述器上控制器为空 = 没人用）。

### 为什么通常不建议走 Action 层

Action 是很多姿势插件的家（移动增强、姿势系统、互动玩具都可能合并进去）。
而 `VRCPlayableLayerControl` 拨的是**整个 Action 可播放层的权重**，不是某一层 ——
多家共用一个开关，谁退出谁就把别人的姿势掐掉。
另外 Action 是全身接管，开着的时候走动会滑步。

先查清 Action 上已经有几家再决定。

### 走丙的三个坑

**① 叠加 clip 不能写恒定值。**
人形叠加算的是「当前帧 − clip **首帧**」（脚本生成的 clip 没有 additive reference pose，
只能拿首帧当参照）。恒定 clip 的增量恒为 0，表现是**纹丝不动**，
而曲线、遮罩、权重、状态机全对，编辑期完全看不出来。

写成 `t=0 → 0`、`t=RAMP → 目标值` 的斜坡，clip **不循环**（否则来回抽搐），
播完停末帧。这样在两种可能的语义下结果相同，不用猜：

| 语义 | 增量 |
|---|---|
| 当前帧 − 首帧 | v − 0 = **v** |
| 直接相加 | **v** |

**② 层混合模式要设成 Additive，不是 Override。**
Additive 可播放层的层 0 常常是 VRChat 自带的呼吸微动（含手臂曲线）。
用 Override，Idle 的空 clip 会把手臂上的呼吸**抹成 0**。

**③ 姿势不出来时先排除「可播放层权重为 0」。**
在状态上挂 `VRCPlayableLayerControl(Additive → 1)`，幂等、无副作用，
关掉时**不要**拨回 0（自带的呼吸层还要用）。

### 手指层用权重驱动

手指要「只在需要时接管」，遮罩做不到（同上），所以用权重：

```
层 N   控制层    遮罩＝全关（什么都不写，只用来挂行为）  权重 1
  ├─ Idle   空 clip   行为：TrackingControl 手指→Tracking、LayerControl(层 N+1 → 0)
  └─ 开     空 clip   行为：TrackingControl 手指→Animation、LayerControl(层 N+1 → 1)
层 N+1 手指层    遮罩＝仅手指                          权重 0
  ├─ Idle   空 clip
  └─ 开     姿势 clip（手臂曲线被遮罩挡掉，只取手指）
```

要点：
- 控制层的遮罩必须是**全关**。若给它一个含手指的遮罩，空 clip 又会把手指压成零姿势。
- 权重 0 的层，**状态机照常求值、行为照常触发** —— 这是这套做法成立的前提。
- 两层可以指向**同一份 clip**，靠各自的遮罩各取所需，不用拆成两份。

### ⚠ `VRCAnimatorLayerControl` 的层号必须烘焙后回读

它填的是**本控制器内**的层号。合并进可播放层时层会**重新编号**，
靠 NDMF 的层号重映射服务跟着改。指错了的话那一层永远拨不上来，
而**源工程里完全看不出对错**。

→ 改完必须烘焙一次，读合并后的控制器，确认 `LayerControl` 指向的层名对得上。

### 桌面与 VR 的差别（决定要不要额外做事）

- **桌面**：手臂完全由动画驱动 —— 上面这些问题都在这里发生。
- **VR**：手臂由手柄 IK 接管，**动画里的手臂姿势默认看不见**。
  要让它生效，得在状态上把 `TrackingControl` 的 **`trackingLeftHand`/`trackingRightHand`
  设成 Animation**（只设手指是不够的）。代价是那段时间真手不再驱动虚拟手臂。

所以「桌面模式手臂不对」和「VR 里姿势不出现」是两个独立问题，各有各的修法。

### 还有第三个嫌疑点：`isDefault`

`baseAnimationLayers[i].isDefault` 为 true 时，描述器上的 `mask` / `animatorController`
**会被忽略**，用的是 VRChat 内置那套。设遮罩的同时要一并处理。
手臂这一路查的是 `baseAnimationLayers[2].isDefault`。

> 改完**立刻复核场景里那个字段的实际值**，别假定代码跑过就设上了。
> 场景重载、prefab 覆盖、别的工具重跑都可能把它冲掉 ——
> 工程A 上就出现过「代码写了、场景里还是 `vrc_HandsOnly`」。
> 复核办法：在场景 YAML 里搜 `propertyPath: baseAnimationLayers.Array.data[2].mask`，
> 看 `objectReference` 的 guid 落在哪个文件上。
> （场景 YAML 里中文名是 `\uXXXX` 转义的，搜中文搜不到，要先解转义。）

优先级：VRChat 的可播放层顺序是 Base → Additive → **Gesture** → Action → FX，
Action 会盖住 Gesture。所以「排在 GoGoLoco / AvatarPoseSystem 之下」这个诉求，
用 Gesture 层天然满足 —— 那两个插件的姿势走 Action。
