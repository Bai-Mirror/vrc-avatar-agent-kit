# 生成器实现坑 · 落盘与幂等

> ← [生成器实现坑（索引）](../生成器实现坑.md)　上级：[60 · 菜单与动画层](../../60_菜单与动画层.md)

这页解决的问题：生成器**写资产、改名、重跑、烘焙克隆**时的坑 —— 症状像逻辑写错，根因在资产落盘与幂等。

## 四个必踩的坑

**① 「切换 A 时顺手关掉 B」要用 ParameterDriver 改参数，不要在 clip 里写 B 控制的属性。**
改参数是「关一次」，之后还能再开；写属性等于一直按着，等于把 B 废掉。
> 实测：第一版就是这样让帽子永远打不开。

**② 注意「播一次就停」的厂商层。**
有的层是 `A → 播完 → 无条件跳 Empty` 的结构，进 Empty 后不再写任何属性。
你若在别处覆盖过它管的属性，值会**永久卡住**。
> 实测：猫耳「换发型再换回来就消失」正是如此。

**③ 生成的资产可能是空的，还不报错。**
`AssetDatabase.CreateAsset` **先落盘、再往 List 里加内容、再 SetDirty + SaveAssets** ——
这次改动不保证刷得出去。同一次生成 7 个菜单资产，4 个正常、3 个落盘是空的。
> **正确写法**：先建实例 → **填完内容** → 最后统一 `CreateAsset`（按依赖顺序，叶子在前）→ **回读校验**。
> **发现手法**：比对同一资产在各次提交的字节数 —— 空菜单约 330 字节，每个控件约 200 字节。

**④ 捏脸烤进网格后必查表情外推。**
遍历全工程 `.anim`，曲线峰值 + 烘焙量 > 100 即越界。
> 实测 102 个 clip 里 17 个越界，最高 177.7。修法：写入值改成 `100 − 烘焙量`，多关键帧整条按比例缩。

## 生成器必踩的六个坑（2026-09-01 实测，每条都真的踩了）

这一节按「症状 → 根因」写，因为这些坑的共同点是**症状具有误导性**：
看起来像逻辑写错，实际是资产落盘、渲染取图、参数取值这类底层问题。

### ① 先填内容再 CreateAsset，落盘后必须回读校验

**症状**：生成报告说「覆盖 16 个物体」，落盘的 `.anim` 只有 1307 字节、**零条曲线**。
之后所有验收图都是错的，而且看不出为什么 —— 因为脚本自己的日志是对的。

**根因**：`AssetDatabase.CreateAsset()` 之后再往资产上写内容会**静默丢失**。
ScriptableObject 的 List 字段、AnimationClip 的曲线都中招，且**不是每次都丢**（更难查）。

**做法**：在内存里把对象填满，最后一步才 `CreateAsset`。落盘后立刻回读比对条数：

```csharp
int want = AnimationUtility.GetCurveBindings(c).Length;
AssetDatabase.CreateAsset(c, path);
// … 全部生成完之后 …
AssetDatabase.SaveAssets(); AssetDatabase.Refresh();
int got = AnimationUtility.GetCurveBindings(
    AssetDatabase.LoadAssetAtPath<AnimationClip>(path)).Length;
if (got != want) 报错;
```

**断言放在哪比断言本身重要**：回读必须从磁盘重新加载资产再数；生成过程中间不要有任何 `DeleteAsset` / `Refresh`。


### ⑥ NDMF 手动烘焙会在场景里留一个 `<名字>(Clone)`

**症状**：改了参数、重渲，图却纹丝不动。

**根因**：离屏渲染会把克隆体也当成一个头像渲一遍，文件名多出 `_00_` / `_01_` 索引；
联系表按文件名排序取第一个 → 取到的是**克隆体**的图，而克隆体停在烘焙那一刻的状态。

**做法**：烘焙工具跑完自己清掉新增的 `VRCAvatarDescriptor`；
联系表工具显式排除带索引的文件名（`img_tools.py sheet-by-tag` 已经这么做）。

## ⑦ 菜单资产改名用 `RenameAsset`，绝不删了重建

分区重划时菜单会改名（`配件` → `服装配件`）。
`DeleteAsset` + `CreateAsset` 会换 GUID，**插件 MenuInstaller 的 `installTargetMenu`
和描述器的 `expressionsMenu` 会静默变 null**，落点全丢回根菜单。

```csharp
var err = AssetDatabase.RenameAsset(oldPath, newName);   // GUID 不变
if (!string.IsNullOrEmpty(err)) throw new Exception(err); // 返回值是错误串，不是 bool
```
同理：菜单/参数资产**已存在就清空内容原地复用**，只有 clip 和 controller 是纯生成物可以重建。

**排查引用变 null**：grep 场景 YAML 里那条 `objectReference` 的 guid，与资产 `.meta` 里的 guid 比对，对不上就是这个病。

**材质挂载按「物体名 + 槽序号」显式指定**，不按槽里现有材质的名字匹配 —— 槽是 null 时没名字可匹配，第二次跑时名字又已经变了。

**检查脚本要在修复之前与之后各跑一次**；只在修复之后跑，查不出「修复没做成」。

**菜单引用的参数必须在场景 `ModularAvatarParameters` 里声明**；判据是两个方向的差集都为空；**`localOnly=1` 的参数不占同步位预算**。

## ⑦之二 · `[MenuItem]` 的名字里**不能有 `/`**

Unity 把 `/` 当**子菜单分隔符**。`[MenuItem("Milfy/73 量 脚型（鞋 / 袜 两种场景）")]`
实际建出来的是 `Milfy > 73 量 脚型（鞋 > 袜 两种场景）` 三级菜单，
你想调的那一项**根本不存在** —— `execute_menu_item` 报
「invalid, disabled, or context-dependent」，**看起来像编译失败**。

**判据（先做这个）**：看 `Library/ScriptAssemblies/Assembly-CSharp-Editor.dll` 的时间戳。
比脚本新 → 编译过了，问题在别处（名字、`[MenuItem]` 拼写、类不是 static）。
比脚本旧 → 才是编译问题，去 `Editor.log` 里 grep `error CS`。
⚠ `Editor.log` 是**多个 Unity 实例共用**的，grep 到的错误可能来自另一个工程，看路径确认。

## ⑧ 生成器必须**幂等**：一次调用可能跑了两遍

通过 MCP / 自动化调菜单项时，**超时不代表没执行**；客户端重试会让它跑第二遍。
症状：日志里「改名：无」「对齐改动 0」，看着像没干活，其实是第一遍已经干完了。

**要求**：所有步骤写成「已经是目标状态就跳过」，包括建容器、装第二份实例、改名、对齐场景。
**别用「改动数 > 0」当成功判据** —— 幂等脚本第二遍本来就是 0。

## ⑨ 表里写叶子名，遇到同名会二义 —— 需要一条「完整路径」写法

叶子名解析的好处是换素体/换配色时不用改表。但容器下放两份实例后，
`Jacket` 会命中两个。解析器要在二义时**抛错**（不是取第一个），
同时提供 `X("完整路径")` 这类逃生口给确实需要指名道姓的场合。

## ⑩ 生成完要把**编辑期场景对齐到默认参数**，并做祖先自检

clip 要运行时才生效，编辑期裸状态跟交付态不是一回事。
不要手写一份「该开哪些」的清单 —— **按层序把默认参数选中的状态的 clip 真的应用一遍**，
清单由动画数据自己给出。

顺带做**祖先自检**：凡是默认态要写 true 的路径，逐级往上查祖先；
有祖先关着**且不归任何层管**就抛错。这是唯一能自动拦住「根物体没有主」那一类的判据 ——
组合遍历查不出来，因为它只看被写的路径本身。见
[属性归属与写法](../属性归属与写法.md)。


## 一个字段只能有一个脚本写

### 触发
**同一个工程里已经有一串补丁脚本**（`Fix60A` … `Fix60AB`），你要再加一个，
或者要重跑其中某一个。

### 问
**「我这个脚本要写的字段，前面哪个脚本也写它？重跑那个会不会把我的成果盖掉？」**

补丁脚本天生是**幂等且可重跑**的写法（每个都从头把自己那部分设一遍），
这在**单个**脚本内是优点，一旦两个脚本写同一个字段就变成隐患：
**跑的先后顺序决定最终值，而顺序是人临时决定的。**

### 答错了怎么办
三种处理，按优先级：

1. **合并**成一个脚本 —— 字段只有一个写入点，最干净；
2. 后者**读前者的产物**（前者写文件、后者读常量），并在前者里把常量改到位；
3. 实在要分开：在**两个脚本的文件头**都写明"这个字段由谁最终负责"，
   并让非负责方**跳过**这个字段。

⚠ 不要用「注意跑的顺序」当解法 —— 这个知识只活在当次对话里，下一轮就没了。

### 判据
`grep -l '"_那个字段"' Assets/Editor/<单号>/*.cs`，**命中数必须是 1**。
命中 ≥2 就得按上面处理掉。这条判据两秒，值得在每次加补丁脚本时跑一次。

### 证据（2026-09-08 工程C）
`Fix60X` 和 `Fix60Z` 都写 `_Main2ndBlendMask`：X 挂原始遮罩，Z 挂取反后的遮罩。
Z 修好之后我为了别的事重跑了一次 X，**原始遮罩又被写了回去**，
现象是"刚修好的极性问题自己复发了"，查了一轮才发现是自己盖的。
修法：把 X 里的遮罩路径改成 Z 的产物路径（上面第 2 种），并在两处都写了注释。

### 删目录重建会把**面捕克隆根**上的引用置空（2026-09-19 工程A）
- **触发**：生成器开头 `AssetDatabase.DeleteAsset(<Gen 目录>)` 再重建，而场景里有面捕安装器克隆出的第二个头像根。
- **现象**：Unity 把场景里指向被删资产的引用置空；生成器只按名字接回**原件根**，活着的面捕根上 13 处引用（`_Menu` 的 MergeAnimator、描述器 `expressionsMenu`、各 MenuInstaller）留空。构建后我方 FX 没合进来、菜单断开，AAO 把所有衣服当静态件合成一块——Play 里换整套**看起来什么都没变**，renderer 数骤降（166→114）。
- **问**：「重生成前后，场景对 Gen 目录每个资产的引用数一样吗？」——按 `.meta` 的 guid 在 `.unity` 里计数，与上一次提交逐资产比；少了就是断链。
- **做法**：生成器末尾把原件根上的 Gen 引用按「同相对路径、同类型同序号组件、同属性路径」回填到同名前缀的其它根（只填空、不覆盖），见 工程A `MenuGenA2.MirrorGenRefsToClones()`。更好的是不删目录、原地复用资产（工程B MenuGen60 的写法），GUID 与引用都不动。
