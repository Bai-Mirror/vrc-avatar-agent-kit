# 问题定位 · 观测口径

> **报「X 没生效」之前先问三件事：**
> 这个观测是不是在**正确的时刻**取的？用的**口径**对不对？**校验脚本本身**有没有 bug？
>
> **自信地报一个错误结论，比说「我不确定」代价高得多。**

## 时刻不对

| 场景 | 错误口径 | 正确口径 |
|---|---|---|
| 刚进 Play | 动画器还没求值、NDMF 还没生成完 | 先跑几帧；或用 Gesture Manager 手动切参数 |
| 参数审计 | 编辑期看不到 MA/VRCFury/MenuInstaller 构建期生成的部分 | **Play 模式下跑**（实测编辑期 24 个参数 108 位 → 构建后 92 个 177 位） |
| 材质查证 | 读 prefab YAML 猜 | 写探针脚本让 Unity 报运行时真值 |

## 口径不对

**① 平台覆盖 vs 默认档。**
编辑器渲染**永远走默认档**。改了 Android/WebGL 平台覆盖，编辑器截图**不可能**发现问题。
> 踩过：把某组贴图的 WebGL 覆盖压到 64（默认档仍是 2048），编辑器一切正常，
> 真机上 167 个 prefab 整片发白。

**推论**：性能类改动（贴图预算、压缩格式、mesh 压缩、shader 剥离）都属于这一类。
要么真机验，要么在报告里**明确标注「本项未经真机验证」**。

**② lilToon 的功能开关是 `_UseXxx`，不是 `_XxxBlend`。**
`_MatCapBlend: 1` 但 `_UseMatCap: 0` 时那层根本不生效，
落在该槽的丢失贴图引用是**惰性的，不是 bug**。

**③ Linear 色彩空间。**
工程若是 `m_ActiveColorSpace: 1`，`.mat` 文件里存的是 linear 浮点，Inspector 显示的是 sRGB。
**照着文件里的数字描述颜色会错得离谱。**

**④ 蒙皮包围盒常年虚报。**
`SkinnedMeshRenderer.bounds` 实测把 0.755 m 的素体报到 2.24 m、把 1.15 m 的报到 2.38 m。
量身高用 **Head/Foot 骨骼世界坐标**；要精确取景就**渲一张色键探针反测**
（`通用工具/AvatarPortrait.cs` 的两趟取景）。

**⑤ stripped Transform 的父级要回溯。**
挂在素体骨骼上的对象，父级 fileID 指向的是 stripped Transform，
必须顺 `m_CorrespondingSourceObject` 回溯源预制体才知道真实挂载点。
把 stripped 父级一律折叠到预制体根，会把「分别挂在左右手食指上的两个对象」
误判成「同父同坐标的重复实例」。
另外素体骨骼来自 FBX 导入，fileID 是 Unity 哈希生成的、不在任何文本里出现，**无法反解出骨骼名**。

**⑥ 别用文件名判断服装兼容性。** → [50 装配](../50_服装发型装配.md)

## 校验脚本本身有 bug

> 实测：写了个跨块的非贪婪正则去复核动画曲线，据此报告「文件没改干净」。
> **实际早就是对的** —— 正则跨进了相邻曲线块，捞到了不相干的值。

**做法**：校验脚本先在**已知正确**和**已知错误**两个样本上各跑一次，确认它能区分，再拿去下结论。

## 单模型的视觉判断不可信

模型会以置信度 1.0 虚报**根本不存在**的缺陷，而且**自报的 confidence 完全不能预测真伪**。
> 实测（2026-09-01 审定妆照）：被 ≥2 个模型指认的 4 条全部为真；
> 单模型指认的 17 条里，「工程F脚被裁切」「工程F过曝」经复核**均为幻觉**。

**规矩**：按 [05 · 多模型评审规程](../05_多模型评审规程.md) 的三档编成（`通用工具/agy_panel.py`）：日常 `--fast` 单模型快评的每条指认都当「待核」自己复核；
大节点 3 模型交叉，**≥2 个模型独立指认的才直接采信**，单模型指认降级为「待核」，**不直接丢也不直接信**。

## 「完成」不等于「长对了」

日志写「完成 N 段」只证明代码跑完了，不证明东西长对了。
**视觉资产的正确性只有图能证明**，而且**最少三个角度**。
> 踩过：换栅栏一役连续出过 缩到 1% / 整排转 90° / 集体浮空 1.64 m / 门豁口大 50% / 东端缺一节，
> **五个问题全部由用户看图发现** —— 我每修一个又只拍一个角度就宣布完成。

## 源场景不等于交付态

<a id="源场景不等于交付态"></a>

**在源场景上量出来的数字，不能用来断定交付件的行为。**
构建管线（NDMF / Modular Avatar / 网格优化器）会在烘焙时大幅改写工程：

| 源场景 | 烘焙后 | 谁改的 |
|---|---|---|
| 每个部件一个 SkinnedMeshRenderer | 合并成少数几个 | 网格优化器的自动合并 |
| 渲染器各自的 `localBounds` | 被统一改写 | `MA MeshSettings`（rootBone + bounds + probe anchor） |
| 控制器的层号 | 合并后重新编号 | 各 MergeAnimator 按顺序追加 |
| 可播放层遮罩 | 从「合并后层 0 的 avatarMask」取 | NDMF / VRCFury 一律覆盖描述器上的字段 |
| PhysBone 组件数 | 明显变多（换装骨架合并会各复制一份） | 骨架合并 |

**踩过的实例**：源场景里某发型每个渲染器的包围盒只有 0.1~0.5 m，看着像典型的
「包围盒太小导致视锥剔除」；照着改了之后现象反而变**常驻**。
烘焙后一量才发现：渲染器已被合并成一个，`MA MeshSettings` 把包围盒统一改成 2×2×2，
出界骨 0 —— **交付件里根本不存在小包围盒**，修的是一个不存在的病。

**规矩**：
- 凡是「构建期可能被改写」的属性（包围盒、遮罩、层号、渲染器数量、组件数），
  **判据必须在烘焙克隆体上取**。
- 诊断脚本写成「场上有克隆体就优先量克隆体」，并把量的是谁**打印出来**。
- 烘焙很贵，别循环调；量完把克隆体清掉，别留在场景里。

## 渲染与取景：图渲出来了 ≠ 画上去了

**日志全 PASS、图却是纯色**；出图的 batchmode 不能加 `-nographics`；
连拍多组要每组重载场景否则出重复图；工具主本与工程副本会分叉；
分区量像素差要先证明量的是那个部位；**编辑期改完形态键要渲两次**，单次拍到的是旧蒙皮。
六条都带触发器与判据 → **[观测口径/渲染与取景](观测口径/渲染与取景.md)**

> 一句话记住：**「wrote xxx.png 1500x1500」只证明文件写出来了，不证明画上去了。**
> 送审前先 `getextrema()`，连拍后先两两做像素差。

> → [判据本身可能是坏的（四类坏法与自检）](观测口径/判据本身可能是坏的.md) —— 观测通道渲不出目标现象、「看不到」先查 Scene/Game 视图、探针把缺失报成合法值、分辨率不够就把参数推到极端、判据方向可能反了（先问「删掉被测物指标会不会变好」）。
