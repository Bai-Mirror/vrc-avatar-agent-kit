# 问题定位 · 透明排序与抓屏

> 症状长这样：**「透过某个半透明特效，看不见它后面的东西」**，
> 而且换个角度就好了 / 换套衣服就好了 —— 看起来像随机，其实是确定的。

## 先分清是哪一类

三种机制都会造成「后面的东西没了」，判据完全不同：

| 类 | 判据（可查） | 症状特征 |
|---|---|---|
| **A 抓屏时点** | 有材质用 `GrabPass` 类着色器（lilToon 的 Refraction / Gem / RefractionBlur） | 透过它看，**队列在抓取点之后的东西全没了**，背景却是对的 |
| **B 半透明写深度** | `renderQueue ≥ 2500` 且 `_ZWrite = 1` | 它先画就把后画的透明物整片深度剔除；先后取决于包围盒中心到相机的距离 → 换角度就变 |
| **C 视锥剔除** | `SkinnedMeshRenderer.bounds` 小于蒙皮后的实际范围 | **整个渲染器**一起消失，不是少一块 |

C 见 [观测口径](观测口径.md#源场景不等于交付态)（注意源场景的 bounds 往往不是交付态的）。

## A · 抓屏时点：这是最反直觉的一类

### 机制

`GrabPass { "_lilBackgroundTexture" }` 是**具名抓取**。Unity 的规则是：

> **每帧只抓一次，抓取点＝当帧第一个用这个名字的物体**，
> 之后所有用同一名字的着色器**共用那一张图**。

于是 **渲染队列 ≥ 抓取点的东西，透过任何一个抓屏物体都看不见** ——
它们在那张图被抓走的时候还没画上去。

lilToon 里用这个名字的有 **Refraction / RefractionBlur / Gem**（含 Multi 版）。
一个头像上常见的抓屏材质：宝石、光环玻璃、眼部特效、全息面板。

### 为什么表现得像「偶发」

不是排序抖动。**是「那个特效正好挡在目标前面」的视角本来就少。**
体积大、位置固定的东西（背后的挂件、长发）更容易被注意到；
小面板偶尔飘过某个位置才看得见一次。

**另一个真实的「偶发」来源**：抓取点由**当帧最靠前的抓屏材质**决定，
而宝石/光环这类件往往挂在**可开关的配饰**上。配饰一开一关，抓取点就跳，
「有时候看得见有时候看不见」就是这么来的。

### 排查步骤

1. 列出头像上**所有**抓屏材质（着色器名含 `Refraction` 或 `Gem`）及其 `renderQueue`
2. 取其中**最小**的队列 = 当帧抓取点
3. 列出所有 `renderQueue ≥ 抓取点` 的材质 —— 这就是「透过窗体看不见」的完整清单
4. 拿这份清单跟用户报的现象对照，能对上就坐实了

### 修法：两头夹

单改一头往往不够，因为抓取点取的是**最小值**：

- **把抓屏材质整体后移**到一个够大的队列（例如 3050）
- **把要看见的东西前移**到抓取点之前

第二条常常是必需的：只要还剩一个抓屏材质留在前面，抓取点就被它钉住。

> **优先保证行为一致，而不是最优。**
> 如果某个抓屏材质动不了（例如它会被换色动画换回厂商原件，见下），
> 宁可把「要看见的东西」拉到它前面，让**两种情况下表现相同** ——
> 「时好时坏」比「一直不对」更难查也更难交代。

### 动手前的两个陷阱

**① 厂商材质要复制副本再改**，别改原件。

**② 会被换色动画换掉的材质不能动。**
配色若是「平行目录换材质」（`Material/Black/X.mat` ↔ `Material/Pink/X.mat`），
换色时动画把 `m_Materials` 指回厂商那份，你改的副本会被顶掉，
结果是「换个颜色又坏了」。判据：材质路径落在配色的平行目录里。
**我方生成的换色 clip 不在此列**，要把关键帧改指副本：2026-09-18 工程A「头饰色」clip 引用厂商原件（2450），
构建后把场景里的副本顶回去，用户看到「透过头饰发型透明」。可查问句：「所有 PPtr 曲线里引用的抓屏材质，队列是否都 ≥ 抓取点？」

### ⚠ 离屏渲染能不能验这一类，取决于渲染路径 —— 先做正对照再用

2026-09-03（工程A）那条离屏路径里 `GrabPass` 不工作，抓屏类材质被渲成**实心色块**，
拿那种图判断会得到完全错误的结论（把实心色块当成缺陷复现）。
2026-09-18 审查工具 T3 v2（Play 模式、Vulkan、`Camera.Render` 到 RT）里 `GrabPass` **是生效的**：
窗体透射率 t≈1；把另一个抓屏材质的**运行时实例**队列提前到 2450 复现修复前的抓取点，
T3 检出 7 条、归因到发型，改前 0 条（agy 两家支持）。

- **触发时刻**：准备用离屏图判断任何抓屏类（Refraction / Gem）现象之前。
- **可查问句**：「这条渲染路径能不能复现一个我**人为制造**的抓取点问题？」—— 在 Play 里只改 `renderer.materials`（实例，不落盘）的 `renderQueue` 做正对照；复现不了，这条路径就不能当判据。
- **取舍**：「队列表」永远是第一判据（可证、可回读，状态一变就重算，不用渲图）；离屏图只在正对照通过后做补充，最终观感仍以 Play Game 视图为准。

### ⚠ 「折射强度为 0」不代表没在用折射

见过厂商把 `_RefractionStrength = 0` 的折射着色器**当作透明用** ——
面板的「透明」完全是抓屏合成出来的，材质本身没有 alpha。
把它换成普通透明着色器，面板会变成一块**实心板**。

所以：看到折射强度是 0 就顺手换掉着色器，是错的。先想清楚它的透明是哪来的。

## B · 半透明写深度

队列 ≥2500 的材质如果 `_ZWrite = 1`，它先画就会把排在它之后的透明物**整片深度剔除**。
而谁先画取决于**包围盒中心到相机的距离** → 症状必然是「换个角度就没了」。

透明覆盖层写深度基本都是作者笔误。改 `_ZWrite = 0` 即可，
`ZTest` 不动，被不透明物挡住时照样看不见。

**但要先确认它的透明不是抓屏合成的**（见上），否则改完症状照旧。

## 常用查法

一次把三类需要的数据都取出来：

- 每个渲染器每个材质槽的 **材质名 / `renderQueue` / `_ZWrite` / 着色器名**
- 着色器名含 `Refraction`/`Gem` 的挑出来按队列升序 → 第一行就是抓取点
- `SkinnedMeshRenderer` 的 `bounds` vs 它**顶点真正绑到的骨**的位置

第三条注意：`smr.bones` 是全表，里面大半是别的部件用的骨；
要按 `mesh.boneWeights` 里 `weight > 0` 的索引筛，否则会误报一堆。
