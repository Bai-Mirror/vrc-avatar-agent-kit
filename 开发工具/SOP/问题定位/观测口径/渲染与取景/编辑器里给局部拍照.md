# 在编辑器里给局部（眼睛/手/配饰）拍可比对的照片（2026-09-21 工程B）

**触发**：要在 Editor（不进 Play）里反复渲同一个局部，做 A/B 或逐帧序列。

不进 Play 的好处是不动 ProjectSettings、不等域重载；代价是有三个坑，一次都躲不过。

## 1 · 蒙皮是陈旧的 → 一律 `BakeMesh` 成静态网格再渲

`Camera.Render()` 在编辑模式下渲的是**上一帧的蒙皮结果**。同一个同步块里
「改形态键权重 → Render」拿到的两张图会**逐像素相同**，看起来像「改动没生效」。

```csharp
var baked = new Mesh();
smr.BakeMesh(baked, true);                  // useScale=true
var proxy = new GameObject("__Proxy");
proxy.transform.SetPositionAndRotation(smr.transform.position, smr.transform.rotation);
proxy.transform.localScale = Vector3.one;   // 缩放已烘进顶点
proxy.AddComponent<MeshFilter>().sharedMesh = baked;
proxy.AddComponent<MeshRenderer>().sharedMaterials = smr.sharedMaterials;
```
换形态键状态就重新 `SetBlendShapeWeight` → 再 `BakeMesh` 一次，**别**指望 Render 会跟上。
（别改现有 renderer 的 `sharedMesh` 去换网格：绑定姿势/骨骼顺序对不上，整张脸会消失。）

## 2 · 用空闲层 + `cullingMask` 隔离，不要去关别人的 renderer

```csharp
int layer = -1;
for (int i = 31; i >= 8; i--) if (string.IsNullOrEmpty(LayerMask.LayerToName(i))) { layer = i; break; }
proxy.layer = layer;
cam.cullingMask = 1 << layer;
sceneLight.cullingMask &= ~(1 << layer);    // 场景灯摘掉这层，渲完记得还原
var lg = /* 自己的平行光 */; lg.cullingMask = 1 << layer;
```
好处：不碰任何现有物体的 enabled/层，渲完 `DestroyImmediate` 临时物体即可，
场景 `isDirty` 不被污染。VRChat 工程 8–21 层已被占，31 通常空着（**每次现查，别写死**）。

## 3 · 时间要能定死，否则序列不可复现

着色器里写 `_Time.y` 的效果在编辑器里没法精确控制。**给 shader 加一个默认 0 的偏移量**：

```hlsl
_MLTimeOffset ("Time offset (s)", Float) = 0
...
float t = _Time.y * _MLTimeScale + _MLTimeOffset;
```
渲染时把 `_MLTimeScale` 设 0，时间就完全由 `_MLTimeOffset` 决定，逐帧确定性。
默认 0 + 乘 scale 的写法**不改变线上行为**，可以长期留在 shader 里当测试钩子。

**临时改参数别脏资产**：`new Material(srcMat)` 出一个实例、`hideFlags = DontSave`，
改实例不改 `.mat`。

## 4 · 量化比看图靠谱：拿「关掉效果」的同帧当对照

一帧一帧肉眼看会漏。固定做法：先渲一张「把效果关掉」的对照帧（例如把强度设 0），
之后每帧算 `pixel - control`，统计 **增量 > 阈值的像素数** 与 **峰值增量**。
这两个数能直接回答「这效果到底上没上画面」「哪一帧最强」，也能跨方案横向比。

# 编辑期渲图本身的三个坑（2026-09-21 从「渲染与取景」主页并入）

## 5 · 编辑期改完形态键，单次 `Render()` 拍到的是**改之前**的蒙皮

### 触发
**当你在编辑模式下 `SetBlendShapeWeight`（或任何改蒙皮的操作）之后、正要 `cam.Render()` 出图时。**

### 问
**「这张图之前我渲了几次？」** 只渲一次，第一次 `Render()` 只触发蒙皮更新，拍到的是上一帧的蒙皮。

```csharp
smr.forceMatrixRecalculationPerRender = true;   // 或 smr.enabled = false; smr.enabled = true;
cam.Render();
cam.Render();                                    // ★ 第二次才是对的
```

材质属性改动**不受影响**（`SetTexture` / `SetColor` 当场生效），只有蒙皮 / 形态键滞后一帧 ——
同一个脚本里改材质的部分是对的、改形态键的部分是假的，所以藏得深。

### 答错了怎么办
**渲两次**；并且拍任何形态键相关的图之前，先跑一次 **0 vs 100 的对照样本**（拿一个已知差异巨大的键，如全闭眼）：
对照都没差异 → 取图管线坏了，整批图作废。
代价不对称：多渲一次是毫秒级；少渲一次会让整批验收图变成同一张，还会据此把厂商键误判成「没用」。

### 证据（2026-09-08）

| 策略 | 差异像素 | 最大差 | 判 |
|---|---:|---:|---|
| 单次 `Render()` | **0（0.00%）** | 1/255 | ✗ 坏 |
| `forceMatrixRecalculationPerRender` + 双渲 | 88002（23.28%） | 191/255 | ✓ |
| `enabled` 开关 + 双渲 | 88002（23.28%） | 191/255 | ✓ |

症状：一组 5 张闭眼键的「验收图」**4 张 md5 完全相同、第 5 张只差压缩噪声** —— 半闭眼和全闭眼不可能一样，当时就该停。
后来用同一套工具「验证」某个键能不能藏住瞳孔，得到「零影响」，差点据此判定那个厂商键没用。

> **「不同输入渲出相同像素」的排查顺序：先怀疑取图管线，再怀疑输入没生效，最后才怀疑被测对象。**
> 与 3 · 重复图同一家族、不同病因：3 是场景没重载，本条是蒙皮没更新；两两像素差为 0 时**两个都查**。

## 6 · 烘焙**也救不了**编辑期渲图（如果你烘的是同一个陈旧状态）

### 触发
**打算「先烘焙一次、再在编辑器里渲验收图」的时候。**

### 问
**「烘焙后合并控制器里，有没有层在写 `blendShape.Shrink*` / `blendShape.Toe_*`？」**

### 答错了怎么办
有 → 这些收缩键是**动画层**，编辑期不求值，渲出来是**没施加**的样子，图一律作废。
只能 Play 模式（GestureManager）实拍，或者直接请人看一眼。

### 为什么会这样
MA 的反应式组件（ShapeChanger / Object Toggle / Material Setter）**不总是静态烤进网格**。
被控物体如果是**动画切换**的（衣服根挂在换装轮盘上），MA 只能把效果做成条件动画 ——
生成名为 `MA Responsive: <网格名>` 的层。静态烤入只发生在「物体在构建时就固定开着」的情况。

### 取舍
- 想在编辑期渲图 → 得让被控物体在构建时固定开着，但那样就没有换装了，不现实。
- 所以这条基本是**硬约束**：有换装的工程，收缩键类的验收**必须进 Play**。
- 代价不对称：编辑期渲图便宜但**结论是错的**；Play 实拍贵但对。
  错的结论会导致「改一个本来就对的东西」——本单据此白改过一轮换装 clip。

### 证据（2026-09-08 工程C）
烘焙后合并控制器 109 层里有 **15 层** `MA Responsive:`，写 `Shrink_Foot` / `Toe_heels` /
`Toe_highheels` / `Shrink_Knees` / `Shrink_Elbow`。
烘焙体在编辑器里渲出来，LUNALICE 的 `Shrink_Foot=100(Delete)` 完全没生效，脚整只露在鞋外。

**顺带一个能省事的观察**：那 15 层里 MA **自动把形态键传播到所有 `BlendshapeSync` 的网格**
（`Body_base` + 丝袜 + 袜子 + 脚甲一起写）。手写「每个渲染器一条曲线」是多余的。

## 7 · 烘焙体里的路径**不是**源工程的路径

### 触发
**拿烘焙克隆体做任何「按路径找物体」的事**：换装渲图、组合矩阵、强制显示被压物。

### 问
**「这个路径在烘焙体里还叫这个名字吗？」**

### 答错了怎么办
AAO 的拍平 pass 把 `_Acc/Acc_GothicRoseFox/Ears` 变成**根下一层**、名字
`_Acc$Acc_GothicRoseFox$Ears$138`（数字后缀每次烘焙都可能变，别写死）。
`root.Find(源路径)` 返回 null → 后面那句 `SetActive` **静默不执行**，不报错不警告。

解析器要**四级**回退，缺一级就会漏掉一整类件：

| 级 | 怎么找 | 对应哪种改名 |
|---|---|---|
| 1 | `root.Find(源路径)` | 没被动过的 |
| 2 | `路径.Replace('/', '$')` 前缀匹配根下子物体 | AAO 拍平：`_Acc/X/Ears` → `_Acc$X$Ears$138` |
| 3 | 按末段匹配 `$<name>` / `*$<name>$*` | 拍平后中段被截 |
| 4 | **全树按末段裸名找，唯一命中才采信** | **BoneProxy 搬走的件在烘焙体里是裸名**（`HeadDress`，不带任何 `$`） |

⚠ 第 4 级必须带「唯一命中」这个前提，否则同名件会随便挑一个。找到 ≥2 个就报「歧义」，别猜。

### 判据（不用人看图）
渲完一批图逐张算 MD5，**任意两张逐字节相同 = 状态没切到，图不可用**。
真实渲染有抗锯齿抖动，同一状态两次渲染都未必逐字节相同，何况不同状态。

### 顺带
AAO 会**真的删掉从不启用的物件**（本单 `Rose_Ears`/`Roses_Tail` 四档全写 0 → 烘焙体里不存在）。
按路径找它们会 null，这是正确优化不是缺陷，别去"修"。

### 证据（2026-09-08 工程C）
冲突特写十格，前一版六张里有四张 MD5 相同 —— 十张渲的全是「一件衣服都没穿」的同一状态。

## 8 · 标注图写中文别用 PIL 默认字体（2026-09-21 作者当场指出）

`ImageFont.load_default()` 以及不指定 font 的 `ImageDraw.text()` **没有 CJK 字形**，
中文会渲成一串方框（tofu）。这一条只有拿到图的人能发现，脚本不会报错、日志一片 PASS。

```python
import sys; sys.path.insert(0, "开发工具/通用工具")
from cjk_font import cjk_font
d.text((8, 8), "电光青", font=cjk_font(21), fill=(238, 238, 243))
```

`开发工具/通用工具/cjk_font.py` 会依次试
`NotoSansCJK-Regular.ttc`(index 2 = SC) → Sarasa → NotoSerifCJK，
并且**验一下「电」和「□」的 bbox 不相等**才返回 —— 找不到就抛错，不静默退回方框。

> **可查问句**：这张图上的中文，我是**看过渲出来的结果**，还是只看了脚本没报错？
> 取舍：宁可抛错也别静默降级——方框图发给客户比脚本崩了更贵。
