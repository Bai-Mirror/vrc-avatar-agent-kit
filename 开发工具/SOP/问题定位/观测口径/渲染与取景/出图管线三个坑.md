# 出图管线的三个坑：纯色 · `-nographics` · 重复图

> 从 [`问题定位/观测口径/渲染与取景.md`](../渲染与取景.md) 拆出的子页。接手自主页原第 1~3 节；主页剩下的「主本与工程副本分叉」「分区判据」已重编为第 1、2 节。

## 1 · 日志全 PASS，图却是纯色

### 触发
**当你正要把一批渲染图送去评审、或发给用户/客户之前。**

### 问
**「这些 PNG 的像素极值是多少？」**

```python
from PIL import Image
im = Image.open(p).convert("RGB")
print(im.size, im.getextrema())   # ((205,205),(205,205),(205,205)) = 纯色 = 什么都没渲上
```
更省事的近似判据：**跟同机位的已知好图比字节数**。空白图小一到两个数量级。

### 答错了怎么办
**别送审，回去查取景。** 送一批空白图去评审，模型会认真评论背景色，
而你会把「零条指认」误读成「通过」。

### 证据（2026-09-06 工程C）
- 日志**从头到尾全 PASS**：形态键索引校验 PASS、清零 526/526、12 条键逐条回读正确、
  `wrote cand1_1正面.png 1500x1500`、收尾还原 PASS
- **三张候选图 RGB 极值全是 `(205,205)`**，17–31 KB；同机位基准图 1019 KB、极值 `(2,255)`
- 分野在自动取景：好的那次有 `[probe] attempt=0 o=1.150 bg%=91.8 bbox=(90,59)-(293,286)`
  探针行、收敛到 `ortho=0.717`；坏的那次**没有 probe 行**，直接 `ortho=4.946` ——
  把 1.18m 的头像放进十米视野

> **「wrote xxx.png 1500x1500」只证明文件写出来了，不证明画上去了。**

## 2 · 出图的 batchmode **不要加 `-nographics`**

### 触发
**当你正要拼一条要出图的 Unity batchmode 命令时。**

### 问
**「这条命令里有 `-nographics` 吗？它要出图吗？」**

### 答错了怎么办
出图的**去掉** `-nographics`，只留 `-batchmode`。
编译、资源导入、读控制台这类**不出图**的，加着无妨（还更快）。

### 证据与保留意见
子代理实测报告：加了 `-nographics` 之后**相机输出是与场景内容无关的恒定色**
（直接采样相机 RenderTexture 得出）。

⚠ **我没有独立复现这个实验**，所以机制标为「未复现」。
但规则本身是**零成本且语义上就该如此**的：`-nographics` 的定义就是不初始化图形设备，
而渲染必须走图形设备。**默认不加**是低成本的正确选择，不需要等实验。

## 3 · 连拍多组时，复用同一个已加载场景会出**重复图**

### 触发
**当你要在一次 Unity 会话里连续渲多组不同参数（多个捏脸候选、多套配色、多个配饰组合）时。**

### 问
**「我有没有在两组之间重新加载场景？」**

### 答错了怎么办
**每组之间重新 `EditorSceneManager.OpenScene`**，不要只改参数就接着拍。

### 判据（必须做，不能靠肉眼）
连拍完**两两做像素差**，差为 0 的就是重复图：

```python
from PIL import Image, ImageChops
d = ImageChops.difference(Image.open(a).convert("RGB"), Image.open(b).convert("RGB"))
print(d.getbbox())        # None = 两张完全相同
```

### 证据（2026-09-06）
三组候选连拍，**cand2 与 cand3 第一次出来是逐字节相同的**（MD5 一致）。
参数施加明明是对的（回读校验 PASS），是**渲染状态陈旧**。
重新加载场景后再拍，三组两两 sumdiff 40 万–100 万，不是噪声。

> 这条和「1 · 纯色」是同一个家族：**参数对 ≠ 画面对。**
> 凡是「一次会话连拍 N 组」的流程，两两像素差是**必做的收尾判据**。
