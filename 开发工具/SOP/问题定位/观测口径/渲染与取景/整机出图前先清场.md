# 整机出图（定妆照）前先清场：镜头里不该有的三类东西

> 触发时刻：用 `Camera.Render()` 给**整个头像**出图之前（定妆照、发型/服装对照图、交付图）。
> 局部特写（眼睛、配饰）的坑在 [在编辑器里给局部拍照](编辑器里给局部拍照.md)，那页讲的是蒙皮陈旧与隔离；本页讲的是「场景里本来就多出来的东西」。

## 1 · 场景里往往不止一个头像根，而且**位置完全重合**

### 触发
工程同时摆着源头像和面捕版 / 备份根 / Quest 版，`Camera.Render()` 一次把两具身体都拍进去。

### 症状长什么样
**不长得像「两个人」，长得像穿模。** 2026-09-21 工程B实测：粉色发型底下透出大片奶油色发丝，
第三方评审（agy）指认为「启用粉发时没隐藏底模发型，双发型重叠穿模，blocker，退回重拍」——
**位置指对了，原因全错**。那些奶油色头发属于面捕根，源头像这边 `Hair_Front/Head/Side/Twintails` 全是关的。

### 判据（不用人看图）
出图前数一遍：`scene.GetRootGameObjects()` 里**带渲染器的根**有几个。>1 就必须挡。
日志里把挡掉的根名字逐个写出来，图才说得清拍的是谁。

### 怎么做
用 `Renderer.forceRenderingOff = true`：它是运行时标志，**不序列化、不脏场景**，
比 `SetActive(false)` 安全（后者会进场景改动，一旦被保存就是真改了工程）。`finally` 里逐个置回 false。
> 不要用「关掉别人的 renderer.enabled」——那个是序列化字段。局部特写那边推荐的 `cullingMask` 隔离
> 在这里不好用：两个根通常在同一层。

## 2 · 插件的「摆位预览件」是真渲染器，构建时才删

2026-09-21 实测：PCS（Penetration Contact System）在 `Target Objects/Placement Icons (Auto Remove)/…`
下挂着真的 `MeshRenderer`（`GUI/Text Shader` 的红圈靶标 + "Insert" 字样 + 箭头 + 小球），
定妆照胸口整个被盖住。它构建时由 PCS 自己删掉，所以**成品没问题、只有编辑器出图会拍到**。

- **先别赖 gizmo**：VRCFury 的 SPS socket 图示走 `Handles`（`[DrawGizmo]`），只在 Scene 视图画，
  `Camera.Render()` 到 RenderTexture 是拍不到的。先用 `cam.cullingMask = 0` 渲一张：
  非背景像素 = 0 就说明画面里的东西**全是真渲染器**，不是 gizmo，别再往 gizmo 方向查。
- **怎么找**：把可疑位置反投影成世界坐标，列出 bounds 中心在附近、extents 又很小的渲染器。
  按名字 grep（socket/orifice/sps/marker/gizmo）在 PCS 上会**全空**——它的关键词是 `Placement Icons` 和 `Auto Remove`。
- **匹配要窄**：只认作者自己标了「会被自动删」的字样（`Placement Icons (Auto Remove)` / `will be auto removed`），
  别拿 preview/icon 这类词做模糊匹配，会误伤客户真要的配件。

## 3 · 档位不能手动 `SetActive`，要按参数跑控制器求值

### 触发
出「每个发型/每套衣服各一张」的对照图时，图省事写成 `_Hair.GetChild(i).SetActive(true)`。

### 为什么错
一个档位的 clip **既开也关**。2026-09-21 工程B的 Hair 层，每个外购发型档除了开 `_Hair/x`，
还要关掉素体自带的 `Hair_Front / Hair_Head / Hair_Side / Hair_Twintails / Ribbon_Hair / Hairpin / BandAid_Hair`，
另有 `Sup_HairEar` 层负责关 `Kumachan_Ear`（只对其中两档）。只开不关 = 两套头发叠着拍。

### 怎么做
读参数资产的 `defaultValue` → 覆盖要扫的那一个参数 → 拿 `State70.Evaluate/Apply` 求值落地（带快照还原）。
档位取值**从该层 AnyState 的条件反推**（`Greater lo` / `Less hi` 取区间中点），不要手写 `i/(N-1)`：
MA/VRCFury 的分档是 `1/N` 带宽，手算差一点就落到相邻档。

### 顺带
日志里每档写一行「这档开着哪些头部件」，双发型这种错下次不用看图就能发现。

## 4 · 「穿衣命中」断言比的是 `activeSelf`，不是 `activeInHierarchy`

SOP [70 回归](../../../70_回归测试.md)要求定妆照点名交付穿搭并断言「点名 N 件、开了 N 件」。
实现时容易写成 `activeInHierarchy`——**会假失败**：父级 `_Outfit/某套` 关着时，
它子件的 `activeSelf` 仍然是 1（动画写的就是 `activeSelf`），`activeInHierarchy` 却是 0。
2026-09-21 实测这么比「应开 172 件、实开 25 件，差 147 件」，全是假的。

- **判据**：逐条比 `activeSelf == 求值结果`，对不上 0 条才算命中；悬空绑定（场景里找不到该物体）单独计数、不计入分母。
- **另外记一行给人看的**：镜头里真在渲的顶层件清单（遍历 `GetComponentsInChildren<Renderer>(false)` 往上找到顶层父物体）。这条才是「图里穿了什么」。
- **反过来**：问题是「游戏里看不看得见」（例：换整套后原装件会不会漏出来）时，判据是 `activeInHierarchy && Renderer.enabled && 材质非空`，只比 `activeSelf` 会假报——09-23 工程A A-21 读 `activeSelf` 报「非素体档原装件被部位开关写回 1」18 条，实际整套 clip 关的是父物体 `kaguya_cloth`，A-21b 补读 `activeInHierarchy`＋渲图逐字节相同才推翻。**可查问句**：我要回答的是「菜单选中了谁」（`activeSelf`）还是「画面里有没有」（`activeInHierarchy`＋渲染器）？报缺陷前两个都读。

## 5 · 捏脸值要在**落地之后**再记一次

把控制器默认态落进场景后，它的 blendShape 曲线可能覆盖掉 SMR 上已经烘好的捏脸。
日志要记「真拍下去那一刻」的非零形态键，不是进函数时的。
2026-09-21 实测：进函数 3 条，落地后 4 条——多出来的 `extra_shy_1=100` 是 `RJ_EyeBlush` 默认 1 给的腮红，
也就是说**客户端默认就带腮红**，这一条只有落地后再读才看得见。
