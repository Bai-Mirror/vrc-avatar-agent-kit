## 1 · 工具的「主本」与「工程副本」会分叉

### 触发
**当子代理或你自己修改了 `Assets/Editor/` 下的工具脚本之后。**

### 问
**「`开发工具/通用工具/` 里的主本跟工程副本还一致吗？」**

```bash
cmp -s "开发工具/通用工具/X.cs" "<工程>/Assets/Editor/AvatarGen/X.cs" && echo 一致 || echo 已分叉
```

### 答错了怎么办
**把工程副本回灌主本**（工程副本才是真正跑通过的那份），改前先备份。

### 证据（2026-09-06）
`AvatarPortrait.cs`：主本 33,160 B、工程副本 35,171 B。
工程副本里才有让渲染真正跑通的 `ShootOne` 与探针调试日志。
**不回灌的话，下一单从主本起步，这些修复全部丢失** —— 而且会再踩一次同样的坑。

⚠ 顺带：**订单专用脚本**（如 `CommCSetup.cs`）不要留在
`Assets/Editor/AvatarGen/` 这个放通用工具的目录里；交付打包前要清掉它和它的诊断菜单项。

## 2 · 分区判据：**先证明你量的是那个部位**

### 触发
**当你要按「部位」分区量像素差，用来判断某一区的参数有没有生效时。**

### 问
**「我怎么知道这个 y 带真的是眉毛（/嘴/眼）？」**

### 答错了怎么办
**别拍脑袋定坐标。做一次横向带扫描，让改动自己浮出来**：

```python
for y0 in range(250, 900, 40):
    ...  # 每 40 px 一带，算各方案两两 sumdiff / 显著像素，打印成直方图
```

改动集中在哪几带，那几带才是你要量的部位。

### 证据：我在这上面连错两次（2026-09-06）

**错误一：量错了带。** 我拍脑袋把「眉区」定为 y300–380，量出六组两两
**显著像素 = 0**，于是下结论「眉毛键在候选图上是死的，被刘海挡住了」。
后来带扫描显示 **y250–410 全是 0** —— 那一整段是**额头**，本来就没东西会变。
真正的眉区是 **y410–490**。

**错误二：结论方向也反了。** 在正确的带上重量：

| | 眉区 y410–490 显著像素 | 眼区 y490–610（对照） |
|---|---|---|
| 带刘海 | **5,668** | 89,426 |
| 藏刘海 | **22,015** | 102,428 |

眉毛**从来不是「死的」**，带刘海时就有 5,668 个显著像素，藏刘海后涨到 4 倍。
我把「我量错了地方」读成了「那个部位被挡住了」。

### 判据：**零结果必须先排除「量错地方」**

> **分区判据得到 0，第一解释永远是「这一区本来就不该有变化」，不是「参数没生效」。**
> 排除方法：**同一次扫描里必须有一个已知会变的对照带**（本例是眼区）。
> 对照带也是 0 → 数据有问题；对照带正常而目标带是 0 → 才轮到「参数没生效」。

这与 [判据的形状](判据的形状.md) 是同一条规律在空间维度上的版本：
**带对照的判据会当场暴露，不带对照的判据会输出自信的假结论。**

> 顺带保留一条仍然成立的观察：`mouth_corner_angle_up = 15` 在嘴区
> （带扫描确认 y730–810 六组差异为 0，而该带在其他扫描里确有嘴部结构）
> 最大像素差是 **1** —— **幅度太小的键在评审图里等于不存在**。
> 但注意：这一条也要先确认量的是嘴，不能重蹈眉区的覆辙。
