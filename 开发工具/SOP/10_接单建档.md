
## 面捕硬件预设与目标平台分开问（触发：建档问卷阶段）

**「要面捕吗」和「上哪个平台」是两个问题，不能合并成「要面捕的 Quest 版」。** 一个场景里可以同时存在多个头像根、上传时选其中一个：

| 问题 | 问什么 | 不这么问会怎样 |
|---|---|---|
| 面捕硬件预设 | 用户实际用哪套设备？厂商包常把 `[HD(Quest,Pico)+HD(Pico)]` 这种**平台名**写进根名，它指的是**硬件预设**，不是 Quest 平台 | 拿着名字猜，装错一套预设 |
| 目标平台 | PC / Quest / iOS 各要哪几个根 | 少做或多做，或漏掉 Quest 的转换 |

- **判据**：建档时把「设备型号」与「平台」分别落一行；面捕预设与客户设备**逐字对上**（历史实测：工程C场景两个面捕根，`HD(...)` 必须对客户设备，F §7 未核）。
- **达不到怎么办**：设备说不清就写「待确认」，不要用平台名反推设备。

## 约束表：把参数与动骨余量写进去（同阶段）

约束表除了视觉与功能项，**必须加两行资源余量**，否则做到 60/80 才发现超限：

- **参数余量**：`≤256 bit`（Int/Float 各 8、Bool 1）。客户要的开关多时先估「还要给面捕/VRCFury 留多少」，写进约束。
- **PhysBone 余量**：总数 `≤256`。历史实测有工程停在 255/256（零余量），再挂一根就超 —— 面捕、尾巴、配饰都要占位。
- **取舍**：余量写小了客户加功能就超限、要砍；写大了浪费参数位。**判据是两个数都写进 `建档.md`，60 阶段用实测值对账**（见 [60 菜单与动画层](60_菜单与动画层.md)）。

## 挑包（这一步最容易错）

**厂商按素体分别发包，必须挑本素体那一份。** 不能按数字排序取"最新"。

| 症状 | 例子（2026-09-01 Kaguya 单实测） |
|---|---|
| 选到别的素体 | 厂商包常按「素体名＋版本号」命名，别的素体那份版本号更大 → 排序取最新会选错 |
| 选到非包文件 | 部分插件包内附安装视频，按文件名排序排在最后 |
| 漏掉公共包 | 发型包只有 FBX+prefab（2 个文件），材质在 `Materials_*.zip` 里；漏了就是缺材质 |

**做法**：
1. 用 **Booth 商品 ID（`-NNNNNNN` 后缀，纯 ASCII）** 定位商品目录 —— 目录名带 emoji 和全角括号，路径匹配不稳
2. 在 `files/` 里筛文件名含本素体名的
3. **再扫一遍公共包**：文件名含 `material` / `shader` / `common` / `core` / `dlc` 的
4. 没有本素体版的，**不要直接判定不兼容** → 转 [50 装配](50_服装发型装配.md) 的骨骼比对

## 开包核兼容（报价前做，只读，一件几分钟）

**客户素材包 ≠ 全部支持目标素体。** 实测一个 92 件的客户库里 1 件完全不支持本素体、1 件只有别的素体版；
此前默认客户的素材库是为该素体挑的，差点把不能用的件写进方案。报价和排期是按「都能用」算的，
开工才发现装不上就是白做。

### 判据是包里的 prefab / fbx 路径，不是文件名

商品名写「22アバター対応」不告诉你是哪 22 个。列出 unitypackage 里的 `pathname`
（它是 tar.gz，每个资产目录下有 `pathname` 文件，见 [02 子页](02_环境准备与人工介入/建工程与首轮编译.md) 第四节）：

```python
with gzip.open(p) as g, tarfile.open(fileobj=io.BytesIO(g.read())) as t:
    paths = [t.extractfile(m).read().decode().split("\n")[0]
             for m in t.getmembers() if m.name.endswith("/pathname")]
prefabs = [x for x in paths if x.lower().endswith((".prefab", ".fbx"))]
```

逐素体发包的商品会有一串 `Outfit_<素体名>.prefab`，一眼看出支持谁。嵌套压缩包要往下挖两层
（`X.zip` → `X_12_Avatars.zip` → `.unitypackage`）。

三档判法，**便宜的先做，定不下来再往下**：

| 档 | 看什么 | 能得出 | 不能得出 |
|---|---|---|---|
| 文件名 | zip / 目录名里的素体名 | 挑哪个 zip（上一节） | 兼容与否 —— 共用企划按企划名发，同名不同源也存在 |
| **开包 pathname** | prefab / fbx 的名字 | 逐素体发包的商品支持哪些素体 | 通用包（一个 prefab 配全部素体）的名字里没素体 |
| 骨骼比对 | FBX 里的骨名集合 | 最终判据（[50](50_服装发型装配.md)） | 成本最高，留给前两档定不下来的 |

- **别用正则匹配素体名做自动判定**：`Version` 里含 `sio` 会把 Sio 判进去。自动扫只用来筛出可疑项，逐个开包人工复核
- 代价不对称：判「不支持」错了，代价是一次查库 / 一次骨骼比对（分钟级）；判「支持」错了，代价是按错误范围报价 + 装到一半返工。
  拿不准就写**「待骨骼比对」**，不要两头猜

### 同规格素体：一份 fbx 配多个 prefab ⇒ 网格通用，贴图不通用

包里只有一份 `X.fbx` 却给出 `X_<素体A>.prefab` 与 `X_<素体B>.prefab` —— 厂商用同一份衣服网格发给两个素体，
即两者身型贴合度一致，**服装 / 配饰（可能含发型）这类网格件可互通**。

**但推不到贴图。** 脸 / 身体贴图靠 UV；两个素体若是不同作者的原创模型、面捕作者也分别出了独立适配包
（面捕独立 ⇒ blendshape 集与 UV 都不同），贴图就不通。判据：**有没有厂商发过一份贴图同时标两个素体名**；
只见各自单独的贴图包，就按不通处理。

结论写进 `客户需求/素材兼容性核查.txt`；「不支持」的件连同**包里到底有哪些素体版**，回填素材应用表的「不用」列（[20](20_素材清点导入.md)）。

## 素体谱系

**共用素体企划的存在，让"文件名里没有这个素体名"完全不能当兼容性判据。**
先查这个素体属于哪个企划 / 哪个作者，再找同企划的历史工程当参照。

已知：
- **Kipfel** ＝ まめふれんず（Mamefriends）企划 → 衣服作者按企划名发布
- **Kaguya（輝夜）** 与 **Rurune** 同作者、共用谱系（厂商目录都是 `IKUSIA`）
  → 参照工程 `H5-Rurune`、`工程E`

## 缺件怎么办

**先去本机素材库 `<素材库>/` 找，不要让用户重下。**
```bash
ls <素材库> | grep -iE "<关键词>"
ls <素材库>/*<商品号>/files     # 目录名有 NFD 与 emoji，按商品号通配，别手打全名
```
Booth 商品全量库，结构与客户素材包一致（`.booth-meta.json` + `files/` + `images/`）。
**库里往往比客户素材包更全**（Kaguya 单实测：库里还有面捕插件和动态眼贴图，素材包里没有）。
