# 编辑器调用与重发（execute_code / 菜单 / 锁 / 构建崩溃）

## Play 入口与阻断项

**T1/T4 需要 Play，完整衔接尚未验收（09-23 源码核验，未实跑）。** `AuditStateDriver`/`AuditMenuDump` 均为 `RequiresPlayMode=true`；入口是 `AvatarAudit.AuditRunner.RunRequestFromMenu()` / `Tools/AvatarAudit/Run Request`，读 `<工程>/Library/AvatarAudit/request.json`。`auto_play:true` 只调用 `EnterPlaymode()`，不隔离预处理；`sequence` 也依赖编辑器帧泵。

- 现存批处理 `AvatarAudit.AuditBatch.ExportInventory` 只打开场景、做部件盘点、退出，不能跑 T1/T4。启动器的 `--batch` 带 `-quit`；把上述异步菜单方法直接塞进 `--method` 不会自动获得等待 Play、取结果、失败退出的流程。
- `PlayTest.LayerLogic` 只测固定控制器的猫耳层；`BakeTest.Run` 仅烘焙 NDMF，均不能代替完整预处理与 T1/T4。
- **阻断项**：完整批处理入口、可重载的构建头像与全部依赖、Play 钩子隔离、以及「重载产物→T4/T1 完成且无二次预处理」证据，任一缺失都记 `blocked/未测`，继续请求准备与离线盘点。关闭插件后的源头像仍不是成品；旧 `done`/Play 报告不能移作新口径通过证明。

### 自开交互 Unity 的执行前提

以下规程尚待实际工程验收。

1. 先在隔离工程批处理完成本工程完整预处理，保存成功日志、源修订、插件版本、产物路径与根名。产物须为可重载的场景/预制体及持久依赖，不能只留内存克隆或 JSON；菜单、参数、FX、网格/材质须仍能解析。NDMF 默认 `Packages/nadena.dev.ndmf/__Generated` 会在退出 Play 时清理；VRCFury 进入 Play 前也有临时资产清理。`ManualProcessAvatar` 虽有持久目录，仍只跑 NDMF，不补足完整 SDK 链。
2. 同一工程无活 Unity 后，才用 `bash 开发工具/通用工具/unity_run.sh --project "<隔离测量工程>"` 自己启动交互会话。加载已构建产物，目标根唯一且活跃，脚本编译完成；记录原场景路径/脏标志、Play 状态、相关设置与产物依赖快照。用户正在用的会话不接管；有未保存用户改动时不能直接重载或丢弃。
3. **进 Play 前隔离预处理，不能只关 NDMF。** 以 工程A 本地 NDMF 1.14.3 源码为例：保存并幂等设 `nadena.dev.ndmf.config.Config.ApplyOnPlay = false`，读回；`ApplyOnBuild` 是独立开关，完整构建应启用它，不能拿禁用构建规避报错。菜单 `Tools/NDM Framework/Apply on Play` 是翻转操作，不能盲重发。VRCFury 另经 `PlayModeTrigger` 调完整 SDK 链，其开关读 `EditorPrefs.GetBool("com.vrcfury.playMode", true)`；先保存该键是否存在与旧值，再临时设 false 并读回。**EditorPrefs 是同一用户共享配置**，须排除其它编辑器会话受影响；做不到就换隔离用户配置或记阻断。其它模拟器（尤其 Av3Emulator）、工程自定义 Play 回调也须逐一核实隔离；上述两个开关不能担保整工程没有别的入口。
4. 保存恢复快照到 Play 域重载之外，进 Play 后再读回开关，核对完整编辑器日志中没有新预处理执行。请求明确 `auto_play:false`，先 T4 再按其真实参数生成 T1。若出现重触预处理，停止测量并走恢复，不等待交互构建来“补齐”。`warmup_frames` 仅等帧，不能证明完整构建、也不能阻断构建。

### 现有请求样例怎么用

格式见 [T1](../../../通用工具/审查/docs/state-driver-request.md)、[T4](../../../通用工具/审查/docs/menu-dump.md) 请求 §3；旧根名、参数、哨兵须按本轮产物改写。下面两条**分别**写请求文件，换成实际根名及各自新的绝对输出目录；前提未满足不得触发。

```json
{"tool":"menu","avatar":"<已构建根名>","out":"<本轮T4绝对目录>","auto_play":false,"warmup_frames":10}
```

```json
{"tool":"state","avatar":"<已构建根名>","out":"<本轮T1绝对目录>","auto_play":false,"ensure_gm":true,"version_check":true,"reset":"declared","states":[{"id":"default","params":{}}]}
```

默认态仅做入口冒烟，不能替代全状态覆盖与 `reset:none` 真序列。一次触发后轮询各自 `status.json`；T1 要 `state=done`、版本戳通过、`states.json.gm_controlled=true` / `driver=gesture_manager`，并核状态数、回读断言与警告；`driver=animator` 无法验证 VRC 参数驱动器联动。T4 须核菜单/描述器/参数存在、警告与未声明参数，不能只看 `done`（SDK 字段缺失也可能写出空结果）。T1 参数名取自同一产物的 T4。

### 会话结束必须还原

先留报告，再正常退出自己的 Play；故障按 [环境恢复规程](../../02_环境准备与人工介入/B850_Linux环境/内存预算与并发.md) 处理。按快照恢复 NDMF 开关、VRCFury EditorPrefs（原键不存在则恢复为不存在）、模拟器/回调及本次改动的 ProjectSettings，含 `legacyClampBlendShapeWeights`；逐值读回。T1 Cleanup 会保留末态参数，只还原临时 GM/探针设置，不能替代退出 Play。只读测量在确认没有用户未保存改动后重载磁盘场景，核 `activeSelf`、`Renderer.enabled`、引用与设置差异；临时副本不覆盖源场景，不把 Play 派生设置提交进工程。重启后不能假定关闭开关还有效。

## 重发与崩溃

- `execute_code` 超时会被重发（DepCompiler Apply 跑了 4 次）：长的、非幂等操作走「菜单 + 请求文件」。见 [02](../../02_环境准备与人工介入.md) 二-③。
  **⚠ 2026-09-21 更正：`execute_menu_item` 同样会被重发**（工程B 80 贴图分档实测跑了 **4 次**，
  日志 `[Opt80Tex] 执行` 四行）。所以「走菜单」**不是**规避重发的办法，只是换了个入口——
  真正的要求是**菜单动作本身幂等**。该工具改贴图那部分是幂等的（第 2–4 次「改动 0 张」且代码有
  `if (apply && plans.Count > 0)` 保护），所以这次重发**没有造成损失**。
  > **可查问句**：这个操作跑第二遍时，它对**已经做完**的状态会怎么写？
  > 特别是「回滚用的日志/备份」——那正是第二遍最容易被清空的东西。
  **⚠ 2026-09-22 补：文件锁「跑完就删」挡不住重发。** 重发的请求**排在 Unity 主线程后面**，
  要等当前这轮跑完才执行——那一刻锁刚被 `finally` 删掉，于是它堂而皇之又整跑一轮
  （工程B `ParamCost90` 14 分钟跑完，01:23:44 删锁，紧接着第二轮开跑，期间别的 `execute_code` 全部超时）。
  **写法**：`finally` 里**刷新**锁的时间戳而不是删除，冷却窗口从「跑完」起算；要有意重跑先手动 `rm` 锁文件。
  > **可查问句**：我的锁是在「开始」时间上计时，还是在「结束」时间上计时？重发发生在结束之后。
  **⚠ 构建中 Unity 原生崩溃，不是「第几轮」的问题（09-22 更正）**：09-22 01:31 与 01:57 两次崩溃，第二次是**重启后第一轮**。
  gdb 转储里崩溃线程是 `UnityGfxDeviceW`：`VKWindow::Reshape → GfxDeviceVK::AdjustPrimarySwapChain → … → libnvidia-glcore`，
  即 **Vulkan 在窗口改尺寸时重建交换链、进 NVIDIA 驱动崩**（xrdp 的 X 只挂核显，Vulkan 走独显往核显窗口上呈现）。
  「第三轮必崩」是我按次数凑出来的规律，已被推翻；详见 [本机(Linux) 环境](../../02_环境准备与人工介入/B850_Linux环境.md) 图形 API 一节。
  **现行做法（09-23）**：完整构建和NDMF/VRCFury预处理走 `bash 开发工具/通用工具/unity_run.sh --project "<工程>" --batch --method <入口>`，见 [内存预算](../../02_环境准备与人工介入/B850_Linux环境/内存预算与并发.md)。`--project` 必填，`<入口>` 必须是本工程真实存在且可批处理的静态方法。`delayCall` 只适用于必须在编辑器做的其它测量/渲图；它让调用立即返回，但仍须请求标识、单飞锁和完成文件防止重发，不能消除构建崩溃。
  **⚠ 不只菜单：任何单次可能超过 ~20 s 的 `execute_code` 都算重活**（09-22 04:43 工程A 崩溃）：DSH 在 `execute_code` 里直接调
  `AvatarProcessor.ProcessAvatar(克隆)`，NDMF 单个 pass 29–51 s，请求超时被重发，日志里出现**同一段源码重叠执行**（报告文件被同名重写），
  随后崩在 `Baselib_ThreadLocalStorage` 断言 → FMOD `AudioManager::systemCallback` → `profiler_begin` 的 SIGSEGV——**不是 Vulkan Reshape 那条栈**。
  > **可查问句**：是否完整构建/预处理？是则批处理；否则必须在编辑器且超过20秒，才挂 `delayCall`、结果写报告、开头查单飞锁，立即返回后轮询完成标记。
  取舍：增加请求去重与状态记录，减少重复执行；任务书须点名本条。
  `execute_code` 里的两个编译/拦截坑（09-22 DSH 报）：`Object` 与 `System.Object` 歧义，一律写 `UnityEngine.Object`；`File.Delete`/`FileUtil.DeleteFileOrDirectory` 会被 safety_checks 拦，锁文件的删除要带 `safety_checks=false`。

- **编辑器开着时，别从外部改写已打开的 `.unity`（哪怕只改一行）**（09-22 工程A 两次卡死）：Unity 检测到变更会重导场景、连带 NDMF 预览代理重建，随后主线程不再响应，MCP 连续 `Command TCS timed out`，SIGTERM 无效只能 SIGKILL。要还原派生字段（如 `RenderSettings.m_IndirectSpecularColor`）就在编辑器里改完再存，或关掉编辑器后再改文本。
  **完整构建不要靠换一次编辑器调用再跑**：转批处理；克隆在完成测量/持久化后销毁。
  **卡死判据**：CPU≈0、`Library/ArtifactDB-lock` 时间戳不再动、MCP 连续 3 次超时 ⇒ 停手回报 `CRASHED`，由 Claude 按兜底 SIGKILL→删 `Temp/UnityLockfile` 与 `~/.unity-mcp/unity-mcp-status-<哈希>.json`→重开。
