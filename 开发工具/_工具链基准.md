## ⚠ UPM 侧也有基准 —— 这一页原来只写了 VPM，2026-09-06 补

VPM（`Packages/vpm-manifest.json`）之外，`Packages/manifest.json` 里也有必须锁的东西。
**漏了它会在导入 Triturbo FT 框架之后直接编译失败 72 个错误**，而且报错信息
（一堆 `FbxManager` / `FbxScene` 找不到）看不出根因。

| UPM 包 | 版本 | 什么时候必须有 | 离线可得 |
|---|---|---|---|
| `com.autodesk.fbx` | **4.2.1** | 只要装了 **Triturbo BlendShare**（随 FT 框架 zip 一起来） | ✅ UPM 缓存里有 |
| `com.coplaydev.unity-mcp` | git URL | 想用 UnityMCP 驱动编辑器时 | 需联网 |

### 坑：厂商把包散装进 `Assets/Packages/`，UPM 不会解析它的依赖

`com.triturbo.blendshare 1.0.3` 的 `package.json` 里明写 `dependencies: {com.autodesk.fbx: 4.2.1}`。
上一单（工程A）它是正规 UPM 包，装在 `Packages/` 下，UPM **自动**把 FBX SDK 拉了进来（depth 1）。
这一单它是从 unitypackage **散装解进 `Assets/Packages/`** 的 —— 那是厂商在 unitypackage 里指定的落位，
但 **UPM 不读 `Assets/` 下任何 package.json**，所以依赖永远不会自动解析。

**判据**：装完 Triturbo FT 框架后跑一次 batchmode，
`Library/ScriptAssemblies/Assembly-CSharp-Editor.dll` 时间戳没更新 = 编译失败。
**症状特征**：错误全是 `Autodesk.Fbx` 命名空间下的类型找不到。
**修法**：往 `Packages/manifest.json` 加 `"com.autodesk.fbx": "4.2.1"`，不要去改厂商源码。

> 顺带：BlendShare v1.0.3 的 `BlendShapeDataSOEditor.cs:235` **厂商自带一个缺分号的语法错误**，
> 在 `#if !ENABLE_FBX_SDK` 分支里。装了 FBX SDK 之后那个分支不参与编译，所以它平时不暴露。
> 本单已补分号并把原件备份到 `_厂商源码备份/`（在 `Assets/` 外，不会被 Unity 索引）。

### ⚠ 交付前必须从 `manifest.json` 移除 `com.coplaydev.unity-mcp`

它是 **git URL 依赖**，客户那边没网 / 仓库改了 tag 就打不开工程 ——
正是记忆 `archive-dependency-reproducibility` 里让 4 个工程打不开的那类依赖。
开发期可以有，**打包前删掉**。

## 天花板：三个包同时把 SDK 卡在 3.11 以下

这是「不追最新」最硬的理由 —— 从各包 `locked` 段的 `dependencies` 直接读出来的：

| 包 | 对 SDK 的要求 |
|---|---|
| `com.anatawa12.avatar-optimizer` | `>=3.7.0 **<3.11.0**` |
| `dev.vrlabs.av3manager` | `**3.2 - 3.10**` |
| `vrchat.blackstartx.gesture-manager` | `>=3.10.4 **< 3.11.X**` |

**SDK 升到 3.11 会同时打断这三个。** 而 SDK 现在就停在 3.10.4 这个天花板上，
所以「用最新 SDK」目前是个**空选项**，不是取舍。

NDMF 侧：`modular-avatar` 要 `>=1.14.3 <2.0.0-a`，`LLC` 要 `^1.9.0`，`AAO` 要 `>=1.8.0 <2.0.0`
—— NDMF 在 1.x 内升级是安全的，但没有单独升它的理由。

## 什么时候重新核对：**按事件，不按日历**

| 触发 | 怎么发现 |
|---|---|
| ① VRChat 游戏更新导致 SDK 必须升 | **上传被拒**是硬信号，不要靠猜 |
| ② 某个包的 bug 直接卡住流程 | 例如 NDMF 烘焙中止、MA 装配失效、AAO 优化出错 |
| ③ 新素材包声明要求更高版本 | 厂商 README / package.json 的 `vpmDependencies` |
| ④ **一单交付完成后的空档** | 例行，此时升级代价最低 |

**绝不在单子进行中升级。** 理由是 SOP 硬闸②「一次只落一个改动」——
工具链和素材同时变，出问题时无法归因，只能全撤重来。

## 交付后客户那边会怎样

`vpm-manifest.json` 的 `locked` 段**就是冻结**。客户在自己的 VCC 里打开工程时
可能被提示有更新，**但不点就不会升**。我们控制不了他点不点，
所以交付说明里要写一句：「工程已锁定版本，除非遇到问题不建议升级」。
