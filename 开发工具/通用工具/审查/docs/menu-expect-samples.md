## 4. 样例与自测

### 4.1 真实现有研究样例（工程A）

- 期望：`_长程任务_20260918/派工/tmp/w5/期望_工程A_样例.json`（6 条，出处逐条写在 `note`）
- T1：`_长程任务_20260918/审查产出/工程A/seq_CL_verify_v3`（4 个状态）
- T4：`…/seq_CL_verify_v3/09_t4_menu/params.json`

```bash
python3 开发工具/通用工具/审查/menu_expect_check.py check \
  --expect _长程任务_20260918/派工/tmp/w5/期望_工程A_样例.json \
  --t1     _长程任务_20260918/审查产出/工程A/seq_CL_verify_v3 \
  --params _长程任务_20260918/审查产出/工程A/seq_CL_verify_v3/09_t4_menu/params.json \
  --out    _长程任务_20260918/派工/tmp/w5/报告_工程A_样例.md
```

研究模式实跑结果：**比对 29 行 / 业务失败 1 / 缺失 2 / 未覆盖 280 个档态（涉及 93 个菜单参数）**，退出码 1。

- 业务失败：`MMN档 高跟鞋开` 时 `Body_b:Foot_heel_OFF*` 期望 0、实测 **100**。高跟姿态键
  `Foot_Hiheel=100` 与平底姿态键 `Foot_heel_OFF=100` 同时开着 —— 正是 SOP 50 明令禁止的
  「同一状态两个姿态键同时 100」。这是**如实报出的真实不一致**，没有改期望去凑 PASS。
- 缺失 2 条（`原装档`）：样本 T1 没扫过，用 `gen-request` 产出请求，**待构建后实跑**。
- 未覆盖：按新口径逐档/逐态计。老样例只写了 `A2_Outfit` 的中间两档、`A2_HoleHeel` 的 0/1，
  其余 92 个菜单参数一档未测 —— 报告如实标为局部结果，**不假称完整**。老样例的 `A2_Outfit`
  无 `radial_labels`，研究模式按边界推测要求 0/1，故它也进了未覆盖清单（这正是「参数名覆盖 ≠ 行为覆盖」）。

交付模式对同一份样例：`check --delivery …` → 退出码 **2（检查失败）**：`A2_Outfit` 等 27 个连续参数
没有显式 `coverage` 约定，按「连续轴不猜」判为无法确定覆盖（另有业务失败 / 缺失 / 未覆盖 223 档态）。
结论为「不通过（检查失败）」。**没有为了让旧样例通过而放宽判据**，也没有替它编造档数约定。

### 4.2 离线自测

```bash
python3 开发工具/通用工具/审查/menu_expect_check_selftest.py
```

覆盖：零断言拒绝（所有模式）；Bool 只有开态（研究记录 / 交付失败）；有开关两态通过；
Int 与 radial 多档漏一档失败；params 缺失、**params 重名**、歧义匹配、错误取值、未知参数、
**coverage 声明解析错误（`gears:"oops"`、小数 gears、混入非法值、NaN/Infinity、未知字段/参数）**、
连续参数交付无显式约定、`coverage` 缺出处、无法确定覆盖、空检查结果均非零；
**显式连续边界/gears 约定 + 出处才可通过**；**边界数值保持不改写**（要测 0.25 就发 0.25）；
`slot:` 与 `gen-request` 归一化一致；真实现有研究样例保留预期诊断。
全部为合成离线样例，不跑工程测试、不开 Unity。

## 5. 局限（明确没做的）

1. **离散覆盖 ≠ 全组合**：本工具只逐条比对期望点名的离散状态与形态键，不做参数组合爆炸或
   参数间相互影响分析；不可据此宣称「全组合已测」。通过标题也只写「约定覆盖」。
2. **T1 是编辑器构建后口径，不等于游戏端**：T1 在 Unity Play 里跑 NDMF/VRCFury 构建后的控制器
   （可临时补 GestureManager），但 VRChat 客户端的参数压缩、远端同步、SDK 上传链、他人视角的
   最终形态可能与编辑器不完全一致。**PASS 只证明「编辑器构建后一致」**；真机口径另见
   `90_交付打包/上传后自测清单.md`。
3. **远端量化 / 形态键依赖矩阵另见 T5**：轮盘细扫分档、形态键依赖矩阵、收缩键残留等
   「连续区间 / 写者关系」问题用 `t5_shapekey_matrix.py`（`README_T5.md`）。
4. **档数来源有限**：`radial_labels` 是 T4 把同一参数多个 Radial 控件的 labels 合并后的列表，
   个数不一定等于真实档数；`radial_label_derived` 是 T4 的推算。**交付模式不拿这些当档数依据**，
   连续参数必须在 `coverage` 里显式声明并写出处（人工审核）；研究模式才允许推测并标注。**不猜**。
5. **约定出处不做真实性校验**：只查 `source`/`note`（含 `coverage` 的 note/source）是否非空且
   非占位符，**没有**去核对被引用的文件/行号是否真的写出该约定。出处真实由期望作者负责。
6. **断言不与被覆盖参数逐个绑定**：某档有状态且有断言，不等于断言针对该参数的效果；
   覆盖只保证「该档被一个带断言的期望状态设到过」。因此通过标题只写「约定覆盖」，不写「可交付」。
7. **名字匹配靠通配与 T5 还原规则**，跨语言命名（参数叫 Coat、物体叫 outer）时，期望作者要用
   能对上的路径/叶名；匹配不到会明确记 FAIL，不会静默放过。
8. **可见性只看 `renderers[].visible`**（`activeInHierarchy && enabled`），不看材质透明度
   （T1 的 `visibility` 里有 V3/V4，本工具没用）；「半透明但 enabled」会被判可见。
9. 本工具**不判断设计意图**（哪个键该跟谁走、档位该有几档），只把「期望说的」与「实测读到的」
   摆在一起对；对错由期望来源（交付说明/SOP）负责。`params.json` 的重名/名单冲突只报「结构不合法」，
   不代表已判断哪个条目才对。
